### 1. 核心策略：将“起草规则”视为“数据”而非“文本”

我们将 GB/T 1.1-2020 视为待处理的 **源文档（Input）**，利用我们已有的 `CSM Parser` 将其解析为结构化 SSIR。随后，一个专门的 **“审核规则编译器（Audit Rule Compiler）”** 遍历 SSIR，根据 5 种特定模式精准抓取要求。

#### 抽取的 5 大模式锚点（Pattern Anchors）：

| 模式类型 | 典型位置 | 抽取逻辑 |
| :--- | :--- | :--- |
| **模态动词约束** | 第 6~9 章、附录 C | 提取含 **“应”、“不应”、“宜”** 的句子，并按主语（如“文件名称”、“范围”）聚类。 |
| **结构位置断言** | 第 7.5 条（范围）、第 8.6 条 | 识别“应设置为文件的第X章”、“应置于……之后”等位置关系。 |

| **禁止性声明** | 第 5.5.3 条、第 9.4.2 条 | 提取“不应规定……”、“不应与……一起使用”的绝对禁止逻辑。 |
| **附录性质判定** | 附录 A~F 的标题 | 识别“规范性（Normative）”附录，**只抽取规范附录中的“应”**，忽略资料性附录的建议。 |

### 2. 通用程序代码蓝图（基于 Python + Pydantic）

为了做到“通用”（即可扩展至 GB/T 20001.10 或其他起草标准），我们将审核规则本身建模为可序列化的 JSON Schema。

#### Step 1: 定义“审核规则”的数据模型（`AuditRule`）
这将成为后续审核引擎（Quality Engine）的执行指令集。

```python
# packages/core/audit_rule.py
from pydantic import BaseModel
from typing import Optional, List
from enum import Enum

class RuleScope(str, Enum):
    METADATA = "metadata"       # 封面、名称、编号
    STRUCTURE = "structure"     # 章、条、段的层级
    CONTENT = "content"         # 正文表述
    FORMULA_TABLE = "formula_table" # 图、表、公式

class AuditRule(BaseModel):
    id: str                     # 如: GB1.1-7.5.1
    source_clause: str          # 来源条款（如“7.5 范围”）
    scope: RuleScope            # 作用域
    target_path: str            # 对应 SSIR JSON 的 JSONPath，如 "$.metadata.title"
    operator: str               # exists, equals, contains, starts_with, matches_regex
    expected_value: Optional[str | dict] = None
    severity: str               # "error", "warning", "info"
    normative_level: str        # "shall" (应), "should" (宜), "may" (可)
```

#### Step 2: 实现“规则抽取引擎”（Rule Extractor）

这个引擎输入是 GB/T 1.1 的 SSIR JSON，输出是一份 `List[AuditRule]`。核心逻辑如下（`extractor.py`）：

```python
class MetaStandardExtractor:
    def __init__(self, ssir_document: SSIRDocument):
        self.ssir = ssir_document
        self.rules = []

    def extract_all(self):
        # 1. 抽取结构类规则（如“范围必须是第1章”）
        self._extract_position_rules()
        # 2. 遍历所有包含模态动词的段落（抽取措辞规则）
        self._extract_modality_rules()
        # 3. 解析所有“规范性附录”中的表格（抽取映射规则）
        self._extract_table_mapping_rules()
        return self.rules

    def _extract_modality_rules(self):
        # 利用 SSIR 的 ContentElement 遍历
        for node in self.ssir.structuralRoot.traverse():
            for content in node.contentElements:
                if content.presentationType == "paragraph":
                    text = content.textContent
                    # 判定是否为要求型条款（包含“应”、“不应”）
                    if "应" in text and not ("示例" in node.title or "注" in node.title):
                        rule = self._parse_sentence_to_rule(text, node.logicalId)
                        if rule: self.rules.append(rule)

    def _parse_sentence_to_rule(self, text, clause_id):
        # 这是最关键的自然语言轻度解析（规则驱动，不用大模型）
        # 例如：“文件名称应由引导元素、主体元素和补充元素组成”
        if "文件名称" in text and "由" in text and "组成" in text:
            return AuditRule(
                id=f"GB1.1-{clause_id}",
                target_path="$.metadata.title.composition",
                operator="match_structure",
                expected_value=["引导元素", "主体元素", "补充元素"],
                severity="error"
            )
        # 可以扩展无数类似的 if-elif 规则模板，或加载外部 pattern.yaml
        return None
```

#### Step 3: 精准处理“附录 C（情态动词）”这一特殊结构
GB/T 1.1 的附录 C 是**最精确的结构化要求**（表 C.1 明确规定了“应、宜、可”的等效表述）。 
**针对表格的通用抽取逻辑**：

```python
def _extract_table_mapping_rules(self):
    for table in self.ssir.tables:
        # 如果表头含有“能愿动词”或“条款类型”
        if table.caption and ("能愿动词" in table.caption or "条款" in table.caption):
            for row in table.rows:
                # 将表格行转化为规则：严格禁止“必须”作为“应”的替代词
                if "必须" in row.cells[0].text:
                    self.rules.append(AuditRule(
                        target_path="$.content.*.text",
                        operator="not_contains",
                        expected_value="必须",
                        severity="error",
                        source_clause=table.caption
                    ))
```

### 4. 处理大模型的局限性（关键红线）

您与其他大模型对话时，它们可能会建议用 NLP 或 LLM 直接抽取。**请务必将我们 M1 的工程红线传达给它们**：

1. **绝对不依赖 LLM 进行抽取**：要求（如“文件名称应由……组成”）是确定性逻辑。用 LLM 抽取会带来幻觉（漏抽或错抽）。必须使用 **正则表达式 + 结构化模板** 进行编译。
2. **“要求”与“示例”的分离**：GB/T 1.1 中大量“不应”出现在“示例”或“注”中（如“注：不使用‘必须’……”）。抽取器必须通过 SSIR 的 `presentationType`（是否为 `Note`/`Example`）**自动过滤**这些非规范性内容，只从**条文（Paragraph）**中抽取，否则会产生大量误报（False Positive）。
3. **输出必须为可执行的 `AuditProfile`**：抽取的最终产物不是一个文本报告，而是一个 **JSON/YAML 配置文件**。这个文件将直接喂给 M2 的 `QualityAssessor`，对用户上传的新标准进行自动化格式审查。

将 GB/T 1.1 的规则分流处理，是避免系统日后变得臃肿不堪的关键决策。以下是针对你这一想法的系统性技术落地建议：

### 1. 为什么必须将“编排格式”排除出审核？
- **现实世界的多样性**：用户提交的 Word 或 Markdown 草稿，其字体、行距、空格往往不标准。如果将“字号五号黑体”作为审核硬错误（Error），系统会拒绝大量内容准确但排版粗糙的草案，失去实用价值。
- **逻辑层级不同**：**内容/结构**是“语义事实”（Semantic Facts），而**排版/格式**是“呈现表现”（Presentation）。我们的 `SSIR` 存储的是事实，审核校验的是事实的完整性与逻辑性，不应干预表现层。

### 2. 为什么必须“抽取”编排格式（留给渲染）？
GB/T 1.1 的第 9 章（编排格式）和第 10 章（字号字体）包含大量**可量化的精确指令**（如“章编号顶格起排，空一个汉字间隙”、“表头粗实线”）。这些如果不抽取，在 M2（生成 PDF 标准文稿）时，工程师又得回头去翻标准文档手写硬编码。**现在抽取出机器可读的配置，M2 阶段就能直接自动化执行，无需重复劳动。**

### 3. 架构升级：拆分“抽取管线”为双路输出

在你的通用抽取程序中，不应只生成一份 `AuditRule` 列表，而应生成**两份独立的制品（Artifacts）**。我们修改之前的 `MetaStandardExtractor`，在抽取瞬间就根据规则类型进行分流：

```python
class ExtractedStandardKnowledge(BaseModel):
    # 制品 A：用于审核（质量诊断）
    audit_profile: List[AuditRule]  
    
    # 制品 B：用于逆向生成（M2 渲染器专用配置）
    rendering_manifest: RenderingManifest 

class MetaStandardExtractor:
    def extract_all(self, ssir_document):
        for clause in ssir_document.structuralRoot.traverse():
            
            # 关键分流逻辑：根据章节位置判断归属
            if self._is_layout_clause(clause): 
                # 如果属于第 9 章、第 10 章或附录 F（字体表）
                # -> 绝不生成 AuditRule，全部编译为 RenderingManifest
                self.rendering_manifest.update(self._parse_layout_rule(clause))
            else:
                # 其他章节（范围、术语、引用、模态动词）
                # -> 生成严格的 AuditRule
                self.audit_profile.append(self._parse_audit_rule(clause))
```

### 4. 两种制品的具体形态定义

#### 制品 A：`AuditRule`（只校验逻辑、结构和措辞）
**适用范围**：第 5~8 章（名称、结构、层次、要素）、附录 C（能愿动词）。
**绝不包含**：字号、行距、空格数量、页边距。
**示例**：
```json
{
  "id": "GB1.1-7.5",
  "description": "范围应设置为文件的第1章",
  "severity": "error",
  "target": "$.structuralRoot.children[0].title",
  "operator": "equals",
  "expected": "范围"
}
```

#### 制品 B：`RenderingManifest`（排版样式字典）
**适用范围**：GB/T 1.1 的第 9 章、第 10 章、附录 F。
**用途**：直接喂给 M2 的 DOCX/PDF 渲染引擎。
**示例**（将标准原文转化为 CSS/样式键值对）：
```yaml
# rendering_manifest.yaml
layout_rules:
  - element: "章标题"
    font_name: "黑体"
    font_size: "五号"  # 对应 10.5pt
    alignment: "left"
    space_before: "1行"
    space_after: "1行"
    indent: "顶格"
  
  - element: "条文（段）"
    font_name: "宋体"
    font_size: "五号"
    indent: "空两个汉字起排"  # 即 2em 缩进
  
  - element: "表头"
    line_type: "粗实线"
    alignment: "居中"
```

### 5. 关键的区分算法（如何判定某条是“编排格式”？）

你的抽取程序不需要复杂的 NLP。只需利用 **GB/T 1.1 自身的 SSIR 结构**即可精准区分：

- **章节匹配**：如果当前节点的 `logicalId` 属于 `"9"`、`"10"`、或附录 `"F"`（字号字体），或标题包含“编排格式”、“字号和字体”、“幅面” ——> **自动分流至 `RenderingManifest`**。
- **附录性质判定**：必须检查附录的类型。如果附录是“规范性”（如附录 F），其内容必须被渲染器严格执行；如果附录是“资料性”（如附录 A 层次示例），它只是给起草者看的例子，**不应抽取为任何规则**（既不入审核，也不入渲染）。

### 6. 这样做带来的巨大工程红利

#### 第一步：定义规则分类器（Rule Classifier）

    def _route_clause(self, node: StructuralNode) -> str:

def _compile_table_rules(self, table: Table):

**引擎 B：情态动词条文抽取（含位置过滤）**

```python
def _extract_modality_sentences(self):
    for node in self.doc.structuralRoot.traverse():
        # 关键过滤：跳过“示例”或“注”中的内容（它们不是规范性要求）
        if "示例" in node.title or "注" in node.title:
            continue
        
        for content in node.contentElements:
            if content.presentationType != "paragraph": 
                continue
            text = content.textContent or ""
            
            # 无 LLM：仅使用正则匹配主谓宾结构
            # 匹配模式：“X 应 Y” 或 “X 不应 Y”
            import re
            patterns = [
                (r'([^，,。.]*?(?:文件名称|范围|条款|编号|标题|图|表)[^，,。.]*?)应([^，,。.]*)', 'shall'),
                (r'([^，,。.]*?(?:文件名称|范围|条款)[^，,。.]*?)不应([^，,。.]*)', 'shall_not'),
                (r'([^，,。.]*?(?:文件名称|范围)[^，,。.]*?)宜([^，,。.]*)', 'should')
            ]
            for pattern, severity in patterns:
                matches = re.findall(pattern, text)
                for subject, predicate in matches:
                    self.audit_rules.append({
                        "type": "wording_rule",
                        "subject": subject.strip(),
                        "predicate": predicate.strip(),
                        "severity": severity,
                        "source_clause": node.logicalId
                    })
```

**引擎 C：结构位置断言（针对第 7 章）**

def _extract_structure_assertions(self):

                "expected_title": ch.title,
                "operator": "exact_match"
            })

def classify_audit_rule(rule):

### 1. SSIR 的“天花板”：只能做“原子级”与“局部级”检查

- **词法检查**：“这段话里是否包含了‘应’或‘不应’？”（✅ 能做）

**它绝对做不了的（也正是完全审查的难点）——跨要素、跨条款的“关联性推理”**：

> **场景 1（跨章引用）**：GB/T 1.1 第 8.6 条规定“规范性引用文件应设置为第 2 章”。SSIR 能检查第 2 章标题对不对，但**无法推理**：“如果正文中规范性引用了某个外部文件，但该文件没有出现在第 2 章的清单中” —— 这涉及 `Reference` 实体与 `Chapter 2` 列表的**缺失关系**。

> **场景 2（类型继承与例外）**：GB/T 20001.10（产品标准）规定“核心技术要素必须是‘要求’和‘证实方法’”，但 GB/T 1.1 只说“核心技术要素是必备的”。仅凭 SSIR 的树状结构，系统不知道“产品标准”继承了 GB/T 1.1 的所有规则，还要额外加上 20001.10 的专项规则，进而发生**规则冲突（重叠与优先级）**。

### 2. 为什么必须建立“本体关系”才能实现完全审查？

本体（Ontology）在这里不是 NLP 领域的“实体识别”，而是 **“规则逻辑的图模型”**。你需要将离散的 SSIR 节点通过**语义边（Semantic Edges）**连接起来，形成可推理的知识图谱。

#### 本体需要显式定义的 4 类关键关系：

| 关系类型 | 示例（GB/T 1.1） | 推理出的审核逻辑 |
| :--- | :--- | :--- |
| **`前置约束`** (Precedes) | “范围”必须在“规范性引用文件”之前 | 如果 SSIR 中“规范性引用文件”的 `sortOrder` 小于“范围”，报错。 |
| **`互斥/替代`** (Excludes) | “术语和定义”与“符号和缩略语”可合并 | 如果两者同时存在且内容重复，提示冗余。 |
| **`派生/特化`** (Specializes) | 产品标准（20001.10）是 GB/T 1.1 的特化子类 | 审核产品标准时，**自动加载** 1.1 规则 + 20001.10 规则（规则继承）。 |
| **`引用闭环`** (Reference Closure) | “规范性引用的文件必须在参考文献中列出” | 遍历 SSIR 中的 `Reference` 列表，若发现引用文件未在前言或引用清单中，触发“悬空引用”错误。 |

### 3. 正确的架构分层（SSIR + 审计本体的协作模式）

不要试图把本体塞进 SSIR 里（那样会让 SSIR 极其臃肿）。正确的做法是 **“以 SSIR 为事实层，在其上动态构建审查本体图”**：

1. **第一层（事实层）**：就是你现在的 **SSIR JSON**。它是绝对权威的“源文本映射”，不包含任何推理逻辑。
2. **第二层（本体加载层）**：系统根据待审文档的 `documentType`（如 `ProductStandard`），从配置中心加载对应的 **`Audit Ontology`**（本质是一个包含节点类、属性、约束边界的 RDF/OWL 或 Property Graph 文件）。
3. **第三层（推理机）**：将 SSIR 实例化为本体的个体（Individuals），运行基于规则的推理（Rule-based Reasoning，如使用 `SHACL` 或 `Drools` 风格引擎）。

**关键优势**：当 GB/T 1.1 修订（比如 2026 版发布）时，你**完全不需要修改 SSIR 解析器**，只需要**更新第二层的 `Audit Ontology` 配置文件**即可。

你的本体只需要定义三种核心“逻辑实体”：
- **`StructuralEntity`**（章、条、附录）

- **`CrossReference`**（引用关系）

> *“附录 B 是规范性的，但正文中没有对应的‘见附录 B’提示？”*

=======================================
那么，将GBT 1.1抽取到SSIR后，是否能够实现基本的格式或结构审查（是否需要借助大模型才能够实现更深入的审查？）？
------------------------------------
这是一个非常关键且务实的追问。我的直接回答是：

**将 GB/T 1.1 抽取到 SSIR 后，完全可以实现 80%~90% 的“基本格式与结构审查”，且完全不需要大模型。但对于“更深入的审查”，大模型并非必需品，而是“锦上添花的辅助工具”——真正实现“深度审查”的核心是“规则引擎 + 关系推理（本体）”，而非大模型。**

为了让你更清晰地规划技术路线，我把审查分为三个层级，并分别说明 SSIR、规则引擎和大模型各自的作用：

---

### 第一层级：基本格式与结构审查（SSIR 完全可以独立完成）

这类审查本质上是**“位置与词法检查”**，SSIR 的数据结构天生就为此而生。无需任何 AI，纯代码即可实现：

| 审查项 | SSIR 如何实现（无大模型） |
| :--- | :--- |
| **必备要素是否缺失** | 检查 `structuralRoot.children` 中是否包含 `title="范围"`、`"规范性引用文件"`、`"术语和定义"`。 |
| **章编号是否连续、正确** | 遍历树节点，检查 `number` 属性是否按 `1, 2, 3...` 递增，条编号是否正确嵌套（如 `5.1` 不能出现在 `5` 之前）。 |
| **附录性质是否标明** | 检查附录节点是否包含 `[规范性]` 或 `[资料性]` 标识，若无则报错。 |
| **列项层次是否超限** | 检查 `ListItem` 的递归深度是否超过 2 层（GB/T 1.1 规定列项细分不宜超过两个层次）。 |
| **图/表编号是否在正文中被提及** | 遍历 `ContentElement` 中的 `figureRef`/`tableRef`，反向验证其是否被 `textContent` 中的“见图 X”所引用。 |

**结论**：只要 SSIR 构建得足够精准（我们 M1 已验证），上述所有检查都可以在 `validator/` 模块中用 **XPath/JSONPath + 循环** 完成，准确率 100%，零幻觉。

---

### 第二层级：逻辑关系与引用完整性审查（需要规则引擎/轻量级本体，但仍无需大模型）

这是你上一轮提到的“跨章推理”问题，例如“规范性引用的文件是否出现在第 2 章清单中？”“术语条目的定义是否使用了陈述型条款？”。这类审查的难点在于**跨节点关联**，但依然**不需要大模型**。

- **实现方式**：在 SSIR 之上构建一个 **“逻辑规则层”（Rule Engine）**，将审查规则编写为可执行的断言脚本（如 `SHACL` 或自定义 Python 函数）。
- **示例规则（伪代码）**：
  ```python
  # 规则：所有在正文中规范性引用的外部标准，必须出现在第2章清单中
  referenced_standards = extract_normative_refs(ssir.body)  # 从正文提取 "GB/T XXXXX"
  chapter_2_list = get_clause_by_title("规范性引用文件").list_items
  for std in referenced_standards:
      if std not in chapter_2_list:
          raise AuditError(f"规范性引用 {std} 未在第2章清单中列出")
  ```
- **是否用大模型？** **完全不用**。这是确定性的字符串匹配和集合运算，写几条规则就能稳定运行一辈子。

---

### 第三层级：语义一致性与意图模糊性审查（大模型的价值所在）

这是你所谓的“更深入的审查”。典型场景包括：

1. **同义反复/逻辑矛盾**：标准正文中同时出现“温度应保持在 25℃ 以上”和“温度不应超过 20℃”。
2. **范围与技术内容不匹配**：标准名称为“咖啡研磨机规范”，但正文核心技术要素却写了“润滑油要求”。
3. **模态动词误用（难以规则化）**：将本应使用“应”（要求）的地方写成了“可”（允许），或使用附录 C 禁止的“必须”替代“应”。

**对于上述场景：**

- **大模型确实能“理解”并发现这些隐患**，它擅长语义对比和上下文理解。
- **但，大模型不是必需的，甚至是有风险的**：
  - **风险 1（幻觉）**：大模型可能会把合理的差异性表述误判为错误（False Positive），或漏掉真正的矛盾（False Negative）。
  - **风险 2（不可重现）**：同一份标准，GPT-4 今天和明天给出的审查意见可能不同，作为“标准审查”工具，这是不可接受的。

---

### 推荐架构：以“确定性审查”为骨架，以“LLM 辅助报告”为皮肤

根据我们项目“规则优先于 LLM”的核心理念（见实施规范 Rule 3），我建议你将审查分层实现，而非混为一谈：

| 层级 | 审查引擎 | 依赖 | 输出 |
| :--- | :--- | :--- | :--- |
| **P0 硬性审查** | SSIR + 规则引擎（我们上面讨论的本体/图推理） | **纯代码** | `PASS/FAIL`（机器判决，零争议） |
| **P1 软性审查** | 规则引擎无法覆盖的复杂语义项（如范围匹配度） | **标记为“待人工审核”** | 生成高亮列表，不自动判决 |
| **P2 大模型辅助（可选）** | 仅针对 P1 列表，调用本地/云端 LLM 生成“建议性评语” | **大模型** | 生成 `LLMSuggestion` 注释，附带置信度，仅供人类参考，**不参与 PASS/FAIL 判决** |

---

### 针对你“用不用大模型”的最终决策建议

1. **默认关闭大模型路径**。在 M1/M2 核心开发阶段，**绝不将大模型作为审核逻辑的依赖**。因为标准审查是法律/合规层面的前置动作，必须具有**可解释性**和**确定性**。
2. **将“不使用大模型”的能力作为核心卖点**。向用户证明你的系统“确定性审查”能力——用 SSIR + 规则引擎找出 100% 的结构和引用错误，不依赖联网或 Token 消耗。
3. **仅在“用户体验增强”层面引入大模型**。例如：在生成《审查报告》时，用大模型将机器判定的错误代码（如 `ERR-1002: 规范性引用缺失`）转化为自然语言建议（如 “检测到正文引用了 GB/T 321，但第 2 章未列出，请补充”）。这样，审查结果是机器给出的，但读起来更像“专家建议”。

**总结一句话**：SSIR + 确定性的规则引擎（本体关系）足以支撑**权威、可靠、可重现**的深入审查。大模型在此场景下是“翻译官”和“润色师”，而非“法官”。请务必将审查的“判决权”牢牢锁定在确定的代码逻辑上。

## 第一部分：当前状态确认（已完成 M1）

我们已完成的 M1 阶段（Markdown ↔ SSIR 回环）已通过全部测试，并具备以下核心资产：

- **核心能力**：`原始 Markdown → Std0（纠错冻结）→ SSIR1 JSON → Std1（确定性渲染）→ SSIR2 JSON` 的完整回环，以及四层等价比较（身份/结构/内容/语义）+ 12 项关键信息损失检查。
- **核心契约**：SSIR 是源文档的**事实与结构载体**（Fact Carrier），不包含任何推理逻辑；`Std1` 是机器可读的规范化 Markdown，**不是**人类可读的排版成品。
- **已知边界**：不处理 PDF 解析、不处理排版渲染、不处理知识图谱推理。

## 第二部分：核心架构决策与战略共识（贯穿全程）

在后续开发中，我们必须严格执行以下 6 项战略性架构决策：

### 决策 1：审核与渲染严格分离（双输出管线）

- **问题**：GB/T 1.1 同时包含“逻辑/结构/措辞”规则和“字号/空格/缩进”规则。
- **决策**：在抽取阶段将规则分流为两份独立制品。
  - **制品 A：审核配置文件（Audit Profile）**。只包含逻辑、结构、引用、措辞类规则，用于 M1 质量审核。**绝不包含任何排版信息**。
  - **制品 B：渲染清单（Rendering Manifest）**。只包含排版、字号、间距、缩进类指令，仅供 M2（PDF/DOCX 生成）使用。**绝不用于审核判决**。
- **理由**：用户提交的草稿排版大多不标准，若将排版规则纳入审核，会导致大量误报，系统丧失实用性。但排版规则必须被抽取，否则 M2 阶段又得人工重读标准，造成重复劳动。

### 决策 2：审核规则配置化，支持动态继承与叠加

- **问题**：产品标准（符合 GB/T 20001.10）既要满足 GB/T 1.1 的通用规则，又要满足 GB/T 20001.10 的专项规则。
- **决策**：审核配置文件支持 `imports`（继承）机制。系统根据待审文档的 `documentType`（如 `ProductStandard`），**自动加载** `gb_t_1_1_base.yaml` + `gb_t_20001_10_product.yaml`，并支持规则覆盖与优先级排序。
- **理由**：避免硬编码，让标准化专家（而非程序员）能够独立维护规则库。

### 决策 3：确定性规则优先，非 LLM 路径为主力

- **问题**：是否依赖大模型实现审查？
- **决策**：
  - **核心审查（P0 级）**：完全基于 **SSIR 结构化数据 + 规则引擎 + 正则/模板匹配 + 表格编译**，实现 80%~90% 的格式、结构、引用审查。**零大模型依赖，零幻觉，完全可追溯、可重现**。
  - **辅助增强（P2 级）**：大模型**仅作为可选插件**，用于将机器判定的错误代码翻译成自然语言建议，或对极少数无法规则化的语义模糊项生成“参考意见”。**大模型的输出绝不参与 PASS/FAIL 判决**。

### 决策 4：从 SSIR 到“轻量级审计本体”，实现关系推理

- **问题**：仅凭 SSIR 的树状结构只能做“孤立检查”（如“第 3 章标题对不对”），无法做“关联推理”（如“正文引用了某标准，但它不在第 2 章清单中”）。
- **决策**：在 SSIR 之上构建 **轻量级关系图（如 NetworkX 有向图）**，显式定义节点间的 `前置`、`引用`、`包含`、`派生/特化` 等关系边。审核规则基于**图遍历算法**执行跨章节、跨要素的完整性审查。
- **关键**：这是实现“完全审查”的**必经之路**。但不必一步到位建立复杂 OWL 本体，先用代码构建内存图，验证可行性后再考虑标准化本体表示。

### 决策 5：规则抽取与规则执行解耦

- **问题**：将 GB/T 1.1 的要求“录入”系统和用该规则“审查”新文档，是两个不同阶段。
- **决策**：
  - **阶段 A（元标准编译）**：将 GB/T 1.1、GB/T 20001.10 等源标准文件作为输入，运行 **非 LLM 抽取器（MetaStandardExtractor）**，输出 `AuditProfile` 和 `RenderingManifest` 两份配置文件。
  - **阶段 B（文档审核）**：将用户待审文档的 SSIR + 加载的 `AuditProfile` 喂给 **规则引擎（Rule Engine）**，运行确定性检查，输出审计报告。

### 决策 6：编排格式“只抽不用”

- **问题**：GB/T 1.1 第 9、10 章及附录 F 包含了大量“字号、字体、缩进、行距、边框”等规则。
- **决策**：在抽取阶段，**完整抽取**这些规则并存入 `RenderingManifest`，但**绝不将其转化为审核规则**。这部分内容仅作为 M2 渲染引擎的自动化配置输入。

## 第三部分：系统架构蓝图（四层模型）

结合以上决策，后续系统将演变为以下四层架构：

| 层级 | 名称 | 输入 | 输出 | 技术实现 |
| :--- | :--- | :--- | :--- | :--- |
| **L0** | **数据采集与结构化层** | 用户 Markdown / 未来 PDF | `SSIR JSON` | 已完成 M1（CSM Parser + Builder） |
| **L1** | **规则编译层（Meta Compiler）** | GB/T 1.1 等源标准的 SSIR | `AuditProfile.yaml` + `RenderingManifest.yaml` | **待开发**：`MetaStandardExtractor`（非 LLM，基于章节路由、正则、表格映射） |
| **L2** | **关系推理与审查层（Reasoner）** | 用户文档 SSIR + `AuditProfile.yaml` | 结构化审计报告（含错误代码、位置、严重性） | **待开发**：`AuditEngine`（含轻量级图推理 + 确定性规则断言） |
| **L3** | **渲染执行层（Renderer）** | 用户文档 SSIR + `RenderingManifest.yaml` | DOCX/PDF 标准文稿 | **未来 M2 开发**：直接映射为排版 API |

## 第四部分：明确的前置工程动作（后续执行清单）

根据讨论，我们在进入大规模开发前，必须按以下顺序完成 5 项预备工作：

1.  **冻结数据模型**：正式定义 `AuditRule`、`AuditProfile`、`RenderingManifest` 的 Pydantic Schema（基于我们讨论的字段，如 `severity`、`operator`、`target_path`、`source_clause`）。
2.  **构建非 LLM 抽取器的核心骨架**：实现 `MetaStandardExtractor` 类，重点攻克：
    - 基于 `clause_id` 的**章节路由分流**（路由至 Audit 还是 Render）。
    - **表格编译引擎**（精确解析附录 C 能愿动词表，将其转换为禁止词映射）。
    - **情态动词条文抽取引擎**（遍历段落，过滤示例/注，用正则提取“应/不应/宜”句子）。
3.  **构建轻量级图推理原型**：在 `validator/` 中引入 `networkx`，实现 `RelationChecker`，重点验证两个核心用例：
    - “引用闭环检查”（正文引用的标准是否出现在第 2 章清单）。
    - “范围前置检查”（规范性引用文件章是否在范围章之后）。
4.  **制定配置文件版本管理策略**：由于 GB/T 1.1 会不定期修订，`AuditProfile` 必须包含 `version` 和 `effective_date` 字段，并支持多版本共存（如 `gb_t_1_1_2020` vs `gb_t_1_1_2026`）。
5.  **明确大模型的接入开关与责任边界**：
    - 在 `config.yaml` 中设置 `llm.mode: disabled|local|cloud`。
    - 大模型模块仅挂载在 `AuditEngine` 的**后处理钩子**上，接受结构化错误列表，输出自然语言注释，并标记 `confidence`。**严禁**将大模型输出转换为审核判决依据。

---

## 第五部分：红线原则（开发中绝对不可违背）

1.  **永不丢弃**：任何未识别的条文必须进入 `UnresolvedRequirement` 列表，供人工复核，绝不能静默丢弃。
2.  **审核不阻断转换**：即使文档违反了 GB/T 20001.10 的核心要求，引擎依然生成完整的 SSIR JSON（仅在 `qualityAssessments` 中标记为 `REQUIRES_REVIEW`）。
3.  **规则优先于 LLM**：能写正则的不写启发式，能写启发式的不调模型。LLM 是“解释器”而非“判决器”。
4.  **版本锁定与可重现**：所有规则编译、审核判决必须基于确定性的代码版本和配置文件，确保同一输入多次运行结果完全一致。
