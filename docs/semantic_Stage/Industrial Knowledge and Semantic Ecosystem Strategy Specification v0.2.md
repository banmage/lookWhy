## 1. 引言

### 1.1 编写目的

本文件旨在为 leleby 与 lookWhy 两个产品体系建立统一的顶层生态战略框架。随着两个项目的独立发展，双方在工业语义、知识模型、分类体系、数据交换等方面存在大量重叠定义和交叉引用，亟需一份共同的"宪法级"文档来明确：

- 两个系统的总体战略关系与定位区分
- 各自的核心任务与边界
- 共享的工业语义基础设施及其治理机制
- 统一的数据分类框架
- 标准化的数据交换与流通机制
- 长期生态演化方向

### 1.2 适用范围

本文件适用于 leleby 与 lookWhy 两个产品体系的全生命周期，包括但不限于：

- 战略规划与产品定位
- 架构设计与技术选型
- 本体开发与语义建模
- 数据治理与安全策略
- 产品迭代与生态扩展

## 2. 总体愿景

### 2.1 生态愿景

构建面向未来智能制造时代的**工业知识与语义基础设施**，使企业工业知识能够被持续积累、治理、复用，并通过标准化语义资产连接全球产品、供应链和AI应用生态。

### 2.2 核心使命

两个系统共同构成完整的工业知识价值链：

> **从企业内部知识生产，到行业知识沉淀，再到全球语义资产流通。**

## 4. 核心边界原则

本章定义两个系统之间最根本的边界，是生态设计的**不可违反原则**。

### 4.1 数据边界

#### 4.1.1 lookWhy 拥有的数据（企业私有知识层 + 项目/型号层）

```
企业私有知识
├── 产品设计知识（含设计原因与决策依据）
├── 工艺知识（含工艺参数与设备信息）
├── 工程经验（含最佳实践与失败案例）
├── 企业内部标准与规范
├── 项目/型号知识（设计记录、测试报告、问题归零）
├── 供应商信息与成本数据
└── 专家隐性知识（经显性化后）
```

**所有 lookWhy 数据的所有权归属企业客户，平台不享有任何数据使用权。**

#### 4.1.2 leleby 拥有的数据（公开产品语义层）

```
公开产品语义资产
├── 产品语义卡（产品名称、型号、分类）
├── 技术能力描述（功能、性能参数）
├── 产品规格（额定值、尺寸、接口）
├── 认证与合规信息
├── 适用标准声明
└── 应用场景与行业适用性
```

### 4.2 不共享原则（核心约束）

以下类型的数据**严禁**从 lookWhy 自动流出至 leleby 或任何外部系统：

- 设计原因与决策依据（为什么这样设计）
- 工艺参数与制造方法
- 供应商信息与采购成本
- 内部测试数据与良率数据
- 失败案例与问题归零记录
- 任何密级≥秘密的知识原子

所有对外输出须经过**独立的脱敏校验**与**双人审批**。

### 4.3 共享原则

两个系统**共享**以下内容：

- 公共工业语义层（本体、元模型）
- 工业分类框架（行业、产品、技术、应用、功能）
- 标准知识模型（Standard、Requirement、Verification、Compliance）
- 测量与单位模型
- 数据交换格式规范

两个系统**不共享**以下内容：

- 企业实例数据
- 企业私有知识图谱
- 用户与权限数据

### 4.4 与标准制定组织的双向关系

lookWhy 与标准组织之间形成双向赋能关系：

| 方向 | 内容 | 说明 |
|------|------|------|
| **标准输入 lookWhy** | 标准组织发布的新标准通过标准更新监测接口进入 lookWhy | 确保企业知识资产基于最新标准 |
| **lookWhy 输出标准组织** | 经脱敏的行业最佳实践、知识图谱可支撑标准草案编制 | 使标准制定基于真实数据 |

标准组织的分类体系可作为**分类框架**的参考来源。

### 4.5 与AI生态的关系

两个系统在AI应用生态中承担不同角色：

| 角色 | lookWhy | leleby |
|------|---------|--------|
| **AI类型** | 工程AI | 商业AI |
| **服务对象** | 企业工程师 | 采购Agent/企业采购 |
| **接口协议** | MCP（模型上下文协议） | HTTP / JSON-LD / MCP |
| **数据范围** | Level 1 完整知识 | Level 3 公开语义资产 |
| **典型场景** | "这个设计为什么这样？" | "哪些产品满足这个采购需求？" |

两个系统的AI接口共享同一套**语义基础设施**（本体、分类框架）。


## 5. 共享基础：工业语义基础设施

两个系统不共享业务数据，但共享一套统一的**工业语义基础设施**。

### 5.1 基础设施层级

```
┌─────────────────────────────────────────────────────────────────────────────┐
│ Layer 5: 应用语义层（Application Semantic Layer）                          │
│  - 面向具体应用场景的语义模型                                              │
│  - leleby: 产品语义卡、采购匹配模型、商业语义资产                           │
│  - lookWhy: 知识原子模型、知识谱系模型、知识资产交换模型                     │
├─────────────────────────────────────────────────────────────────────────────┤
│ Layer 4: 领域语义层（Domain Semantic Layer）                               │
│  - 行业通用的语义模型                                                      │
│  - 产品本体、标准本体、要求本体、验证本体、合规本体、测量本体               │
├─────────────────────────────────────────────────────────────────────────────┤
│ Layer 3: 分类框架层（Classification Framework Layer）                      │
│  - 多维度工业分类体系                                                      │
│  - 行业分类、产品分类、技术分类、应用分类、功能分类、知识领域分类           │
├─────────────────────────────────────────────────────────────────────────────┤
│ Layer 2: 核心本体层（Core Ontology Layer）                                 │
│  - 跨领域共享的核心概念                                                    │
│  - Entity、Organization、Product、Component、Material                      │
│  - Property、Requirement、Measurement、Unit、Time、Location                │
├─────────────────────────────────────────────────────────────────────────────┤
│ Layer 1: 基础语义层（Foundation Semantic Layer）                           │
│  - 最基础的语义框架                                                        │
│  - 顶层类型、关系类型、元模型                                              │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 5.2 核心共享本体

两个系统共同维护以下核心本体：

| 本体 | 说明 | 主要使用者 | 治理方 |
|------|------|-----------|--------|
| **产品本体（Product Ontology）** | 产品分类、结构、组成、属性 | leleby、lookWhy | 生态技术委员会 |
| **标准本体（Standard Ontology）** | 标准结构、版本、引用、适用范围 | lookWhy、leleby | 生态技术委员会 |
| **要求本体（Requirement Ontology）** | 要求类型、约束、强制性等级 | lookWhy、leleby | 生态技术委员会 |
| **验证本体（Verification Ontology）** | 验证方法、测试、证据 | lookWhy | 生态技术委员会 |
| **合规本体（Compliance Ontology）** | 合规判定、证据链、符合性状态 | lookWhy、leleby | 生态技术委员会 |
| **测量本体（Measurement Ontology）** | 单位、量值、精度、不确定度 | 两个系统 | 生态技术委员会 |
| **组织本体（Organization Ontology）** | 企业、部门、角色 | 两个系统 | 生态技术委员会 |

### 5.3 共享语义基础设施治理机制（核心新增）

为确保两个系统语义层的一致性和可维护性，建立专门的治理机制：

#### 5.3.1 治理主体

由**生态技术委员会**负责共享语义基础设施的治理。该委员会由两个系统的核心架构师、本体工程师和行业专家组成，职责包括：

- 核心本体的定义与变更审批
- 分类框架的维护与更新
- 语义版本的规划与发布
- 跨系统语义冲突的仲裁

#### 5.3.2 变更管理流程

```
变更申请
    │
    ├── 来源：leleby 或 lookWhy 任一平台提出
    │
    ▼
技术评估
    │
    ├── 评估变更对各系统的影响范围和兼容性
    │
    ▼
生态技术委员会评审
    │
    ├── 通过 → 发布新版本（含版本号与变更说明）
    ├── 不通过 → 退回申请方，附评审意见
    │
    ▼
同步实施
    │
    ├── 两个系统按升级周期同步更新
    └── 保持对旧版本的兼容（至少1个版本周期）
```

#### 5.3.3 版本与兼容性原则

- 所有共享本体和分类框架须有明确的**语义版本号**（MAJOR.MINOR.PATCH）
- 版本变更须发布变更说明，标注**影响范围**和**升级指引**
- 两个系统在升级周期内须保持对旧版本的**向后兼容**
- **不兼容变更（MAJOR）** 须提前一个版本周期公告，并评估对实例数据的影响

#### 5.3.4 职责分配总览

| 治理对象 | 管理职责 | 变更审批 | 维护角色 |
|---------|---------|---------|----------|
| 基础语义层（Layer 1） | 生态技术委员会 | 委员会一致同意 | 本体架构师 |
| 核心本体层（Layer 2） | 生态技术委员会 | 委员会评审通过 | 本体工程师 |
| 分类框架层（Layer 3） | 生态技术委员会 | 委员会评审通过 | 分类管理员 |
| 领域语义层（Layer 4） | 生态技术委员会 | 委员会评审通过 | 领域专家 |
| 应用语义层（Layer 5） | 各平台自行治理 | 各平台自行审批 | 各平台团队 |

### 5.4 本体治理原则

- **统一来源**：核心本体在生态层统一维护，两个系统不得各自派生
- **版本管理**：本体变更须经过技术评审，确保向后兼容
- **扩展机制**：两个系统可在核心本体基础上扩展应用层专有概念
- **同步机制**：本体变更通过标准化流程在两个平台间同步


## 6. 工业分类框架

两个系统不采用单一分类树，而是采用**多维度工业分类框架**。这是本生态最重要的语义基础设计之一。

### 6.1 分类维度的战略价值

分类框架是工业语义基础设施的核心组成部分。通过将传统单树分类拆解为多维度独立分类，系统能够：

- 避免单一分类树无法表达知识多维属性的困境
- 支持跨维度的组合查询（如"船用 + BLDC + 防水"）
- 为AI采购和工程推理提供精确的语义匹配基础
- 兼容现有国家标准和国际标准分类体系

### 6.2 分类维度总览

| 维度 | 回答的问题 | 参考依据 | 主要使用者 | 是否共享 |
|------|-----------|----------|-----------|----------|
| **行业分类** | 谁在生产/谁在使用 | GB/T 4754、ISIC、NACE | leleby | 是 |
| **产品分类** | 是什么产品 | 产品本体、IEC 61360 | leleby、lookWhy | 是 |
| **技术分类** | 用什么技术实现 | 行业技术分类体系 | lookWhy、leleby | 是 |
| **应用领域分类** | 用在哪里 | 行业应用分类 | leleby | 是 |
| **功能能力分类** | 能做什么 | 功能本体 | leleby | 是 |
| **知识领域分类** | 属于什么知识领域 | GB/T 23703.7 | lookWhy | 是 |

### 6.3 行业分类（Industry Classification）

**回答的问题**：谁在生产？谁在使用？

**依据标准**：
- 中国：GB/T 4754-2017《国民经济行业分类》
- 国际：ISIC Rev.4（国际标准行业分类）
- 欧洲：NACE Rev.2（欧盟经济活动统计分类）

**示例**：
```
制造业（C）
  └── 铁路、船舶、航空航天和其他运输设备制造业（37）
        └── 船舶及相关装置制造（373）
```

**使用场景**：
- leleby：企业行业归属、供应商行业过滤
- lookWhy：知识资产的行业上下文标记

### 6.4 产品分类（Product Classification）

**回答的问题**：是什么产品？

**依据参考**：
- IEC 61360 标准数据元素类型及相关分类方案
- 产品本体（Product Ontology）
- 企业自定义扩展

**示例**：
```
Product
  └── Electric Motor
        └── DC Motor
              └── Brushless DC Motor (BLDC)
                    └── BLDC Motor Module
```

**使用场景**：
- leleby：产品目录、搜索与匹配
- lookWhy：产品知识关联

### 6.5 技术分类（Technology Classification）

**回答的问题**：用什么技术实现？

**示例**：
```
Technology
  └── Electric Drive
        └── Brushless DC
              ├── Permanent Magnet
              ├── Sensorless Control
              └── Field-Oriented Control
```

**使用场景**：
- lookWhy：技术知识关联、专利分类
- leleby：技术能力标签

### 6.6 应用领域分类（Application Domain Classification）

**回答的问题**：用在哪里？

**示例**：
```
Application Domain
  └── Marine Equipment
        ├── Ship Ventilation System
        ├── Ship Pump System
        ├── Ship Propulsion Auxiliary
        └── Ship Control System
```

**使用场景**：
- leleby：采购场景匹配（"我需要船用电机"）
- lookWhy：应用经验关联

### 6.7 功能能力分类（Function / Capability Classification）

**回答的问题**：能做什么？

**示例**：
```
Capability
  └── Rotary Motion
        ├── Continuous Rotation
        ├── Positioning
        └── Speed Control
  └── Fluid Driving
        ├── Pumping
        ├── Fan Driving
        └── Compressing
```

**使用场景**：
- leleby：AI采购匹配的核心维度
- lookWhy：产品能力知识关联

### 6.8 知识领域分类（Knowledge Domain Classification）

**回答的问题**：属于什么知识领域？

**依据参考**：GB/T 23703.7-2014《知识管理 第7部分：知识分类通用要求》

**使用场景**：
- lookWhy：知识管理视图、导航维度

### 6.9 分类框架的语义表达

所有分类维度在知识图谱中表达为**独立的语义关系**，而非单一树状分类：

```
BLDC Motor Module
  ├── hasIndustry → Manufacturing / Electrical Machinery
  ├── hasProductType → BLDC Motor
  ├── hasTechnology → Brushless DC / Sensorless Control
  ├── hasApplication → Marine Ventilation System
  ├── hasCapability → Rotary Motion / Speed Control
  └── hasKnowledgeDomain → Motor Design / Electrical Engineering
```

一个实体可同时拥有多个维度的分类标签，各维度之间相互独立、可组合查询。

### 6.10 分类框架的治理

分类框架由生态技术委员会统一维护，两个系统共同使用：

| 治理事项 | 负责方 | 说明 |
|---------|--------|------|
| 分类维度定义 | 生态技术委员会 | 新增或删除分类维度 |
| 分类节点增删改 | 生态技术委员会评审 | 企业可根据需要申请扩展 |
| 分类与标准映射 | 生态技术委员会 | 维护与GB/T 4754等标准的映射关系 |
| 版本发布 | 生态技术委员会 | 分类框架版本与本体版本同步发布 |

### 7.2 三级数据粒度

| 等级 | 目标场景 | 数据内容 | 安全控制 |
|------|---------|---------|----------|
| **Level 1（完整知识）** | 企业内部系统、内部AI助手 | 完整知识原子、设计原因、工艺参数、经验案例 | 企业内网/零信任认证 |
| **Level 2（受控共享）** | 供应商、客户、合作伙伴 | 产品规格、接口定义、测试规范、维护手册 | 独立授权、NDA、有效期 |
| **Level 3（公开语义资产）** | leleby、行业平台、AI采购 | 产品语义卡（规格、参数、认证、能力） | 脱敏校验、双人审批 |

### 7.3 标准化交换格式：Industrial Semantic Package

两个系统之间的数据交换采用标准化的 **Industrial Semantic Package** 格式：

```yaml
SemanticPackage:
  packageId: string
  version: string
  createdAt: datetime
  source: lookWhy | leleby

  identity:
    id: string
    name: string
    description: string

  classification:
    industry: [string]       # GB/T 4754 行业代码
    product: [string]        # 产品分类
    application: [string]    # 应用领域
    capability: [string]     # 功能能力

  semantic:
    entities: [Entity]       # 知识实体列表
    relations: [Relation]    # 语义关系列表

  content:
    specifications: [Spec]   # 规格参数
    compliance: [Compliance] # 合规信息
    certification: [Cert]    # 认证信息

  governance:
    owner: string
    securityLevel: public | internal | confidential
    authorization: [Auth]    # 授权信息

  provenance:
    sourceSystem: string
    derivedFrom: [string]    # 来源追溯
    versionHistory: [Version]
```

### 7.4 leleby 与 lookWhy 的交换边界

| 交换方向 | 内容 | 格式 | 安全要求 | 说明 |
|---------|------|------|----------|------|
| lookWhy → leleby | Level 3 公开语义资产 | Industrial Semantic Package | 脱敏 + 双人审批 | 主要数据流 |
| lookWhy → leleby | 公共本体更新提案 | Ontology Change Request | 技术评审 | 提案方式，非直接更新 |

| leleby → lookWhy | 市场反馈（匿名化） | Market Feedback | 脱敏 | 不包含企业标识 |

### 8.2 与标准制定组织的关系

- lookWhy 可向标准组织提供**脱敏行业知识**，支撑标准草案编制
- 标准组织发布的新标准通过**标准更新监测接口**进入 lookWhy
- 标准组织的分类体系可作为**分类框架**的参考来源
- 企业可通过 lookWhy 参与标准制定的意见反馈和验证

### 8.3 与AI生态的关系

- leleby 面向**采购AI**提供产品语义数据
- lookWhy 面向**工程AI**提供知识原子服务（通过MCP协议）
- 两个系统的AI接口共享同一套**语义基础设施**
- AI Agent可通过 MCP 协议访问 lookWhy 知识原子和 leleby 商业语义资产


## 9. 治理原则

### 9.1 生态治理原则

| 原则 | 说明 |
|------|------|
| **数据主权** | 企业数据归属企业，两个平台不享有任何数据使用权 |
| **边界清晰** | lookWhy 与 leleby 的数据边界不可模糊，不共享企业实例数据 |
| **语义统一** | 共享本体在两个系统间保持一致，不得出现语义分歧 |
| **安全优先** | 所有数据流通须经过权限判断与安全校验 |
| **可追溯** | 所有跨系统数据交换记录完整审计日志 |

### 9.2 分类治理与本体治理分离

| 治理维度 | 管理对象 | 负责方 | 变更影响 |
|---------|---------|--------|----------|
| **分类治理** | 分类标签体系（行业、产品、应用等） | 生态委员会 | 仅影响检索视图 |
| **本体治理** | 语义关系模型（本体、关系类型） | 生态技术委员会 | 影响语义表达，须双系统同步 |

### 9.3 版本管理

- 所有共享本体和分类框架须有明确的版本号
- 版本变更须发布变更说明，标注影响范围
- 两个系统在升级周期内须保持对旧版本的兼容
