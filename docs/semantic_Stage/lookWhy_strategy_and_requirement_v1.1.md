# lookWhy 企业工业知识资产生产与演化平台 战略与需求说明书 v1.1

---

## 1. 引言

### 1.1 编写目的

本文件为 lookWhy 平台的**战略定位与产品需求基线**，旨在明确平台的核心价值主张、战略边界、用户群体、核心理念、知识体系及功能需求，作为后续架构设计、开发和迭代的根本依据。

本文件聚焦于回答"为什么做 lookWhy"、"lookWhy 是什么"、"解决什么问题"、"服务谁"、"如何与外部系统协同"及"需要具备哪些核心能力"，不涉及具体技术实现方案。

本文件是 leleby & lookWhy 工业知识与语义生态战略规划（v0.2）的下游文档，与之保持战略一致性。两个文档的引用关系为：本文件第2章（产品战略定位）与第4章（核心边界原则）完全遵循生态战略规划所定义的两个系统边界，不另行定义冲突内容。

### 1.2 项目背景

在制造业数字化转型过程中，企业在产品设计、工艺设计及生产制造环节积累了海量知识资源——包括法律法规、国家标准、行业标准、企业标准、专利文献、设计规范、工艺参数、试验数据及工程经验。然而，这些知识当前普遍以非结构化文件（PDF、Word、图纸）或个人经验形式存在，面临以下核心困境：

- **知识流失风险**：核心智力资产随技术人员流动而流失
- **复用效率低下**：分散存储于不同部门和个人手中，缺乏统一治理
- **合规风险突出**：标准版本更新后，设计人员难以精准确认适用版本
- **经验传承困难**：设计决策依据（"为什么这样做"）未被系统化记录
- **核心机密管控薄弱**：工艺参数、供应商信息等核心知识缺乏有效保护

同时，企业核心知识资产（如工艺参数、设计依据、失效模式）具有高度私密性，不得随意对外公开。需要一套系统，既能**深度管理企业内部知识资产**，又能**安全地将企业能力抽象为可对外交换的语义资产**。

### 1.4 与知识管理国家标准的兼容性说明

本系统在知识管理方法论层面参考 GB/T 23703.7-2014《知识管理 第7部分：知识分类通用要求》所确立的知识分类框架，将其作为面向人类用户的**管理视图与导航维度**来源之一。系统不将传统分类树作为底层数据模型，而是采用知识图谱/本体模型作为知识组织的底层表达。分类体系作为图谱之上的可配置视图存在，两者在系统中并存且互不冲突。

本文件使用的核心术语（工业知识资产、工业语义资产、知识原子、语义包、知识资产交换层等）与《leleby & lookWhy 工业知识与语义生态战略规划 v0.2》保持一致。本文件中涉及的两个系统边界、共享基础设施、数据交换机制等概念均以生态战略规划为基准，不另行定义。


## 2. 产品战略定位

### 2.1 项目愿景

构建面向制造企业和行业组织的**工业知识资产生产与演化平台**，使产品设计、工艺设计、标准规范、专利技术和工程经验从静态文件转变为**动态、可计算、可追溯、可验证、可流通**的知识资产。最终形成"企业知识生产 → 行业知识沉淀 → 全球工业语义市场流通"的数据飞轮。

### 2.2 核心定位

lookWhy 的核心定位可以概括为三个层面：

- **对内**：企业核心智力资产的唯一可信源和统一治理中心，回答工程中"为什么这样设计与制造"（Why）的问题
- **对外**：企业工业知识资产的受控流通枢纽，通过权限化输出接口向 leleby、企业其他系统、本地知识工具等提供经过治理和授权的语义资产
- **向上**：支撑行业/团体标准的数字化编制与知识沉淀

### 2.3 核心价值主张

| 价值维度 | 说明 |
|---------|------|
| **知识资产化** | 将分散在个人、文件、邮件中的隐性知识转化为企业级结构化知识资产 |
| **知识可追溯** | 每条知识都记录来源、版本、谱系，支持完整的合规证据链 |
| **知识可演化** | 支持知识的衍生、修订、版本更新，形成持续生长的知识网络 |
| **知识可复用** | 通过原子化、语义化、多维检索，实现知识的精准复用 |
| **知识可流通** | 核心机密严格受控，不同密级和粒度的知识资产可安全输出至不同外部场景 |

### 2.4 与 leleby 平台的边界与协同关系

本节内容遵循《leleby & lookWhy 工业知识与语义生态战略规划 v0.2》第3章和第4章的定义。

#### 2.4.1 独立平行关系

lookWhy 与 leleby 是两个**独立平行**的产品线，而非上下级子系统。二者通过**工业语义基础设施层**实现数据贯通，但实例数据严格隔离。

#### 2.4.2 定位区分

| 维度 | lookWhy | leleby |
|------|---------|--------|
| **定位** | 工业知识资产生产端与流通枢纽 | 工业语义资产消费与交易端 |
| **范围** | 企业内部闭环 + 受控对外流通 | 全球/供应链市场 |
| **管理内容** | 企业私域知识（设计、工艺、经验、内部标准、失效案例） | 企业愿意公开的产品语义卡、技术能力、合规认证 |
| **服务对象** | 产品设计/工艺/标准化/质量工程师、知识管理员、本体工程师 | 企业采购、AI采购Agent、产品发现系统、供应链平台 |
| **回答的问题** | 为什么这样设计与制造（Why） | 有什么产品能力（What） |

#### 2.4.3 数据流转关系

企业内部研发制造过程 → lookWhy（沉淀为私有知识资产）→ 抽象与脱敏（仅提取产品规格、符合性标准、认证信息，不输出工艺/供应商/设计原因）→ 授权审批 → 发布至 leleby。

#### 2.4.4 共享基础设施

两个平台共享**公共工业语义层**（如基础物理单位、标准本体、要求模型、测量模型），但各自维护独立的实例图谱。该公共语义层由生态技术委员会统一治理，独立于任一平台存在。详见《leleby & lookWhy 工业知识与语义生态战略规划 v0.2》第5章。

#### 2.4.5 核心约束

lookWhy **不得**将工艺参数、设计原因、供应商信息、失效模式等核心机密自动同步给 leleby。所有对外输出须经过授权审批与脱敏校验。

### 2.5 知识资产生态流通战略

lookWhy 不是封闭的知识库，而是企业知识资产的**统一治理中心和受控流通枢纽**。知识资产可安全流通至以下三类外部场景：

#### 2.5.1 对外流通的三级数据粒度

系统根据输出目标的不同，提供不同粒度和密级的知识资产：

| 输出等级 | 目标场景 | 包含内容 | 安全要求 |
|---------|---------|---------|----------|
| **Level 1：企业内部完整知识** | 企业员工、内部AI助手、PDM/PLM/MES等内部系统 | 产品设计知识、工艺知识、测试数据、失败案例、设计原因、专家经验 | 企业内网/零信任认证 |
| **Level 2：合作伙伴共享知识** | 供应商、客户、联合研发伙伴 | 产品规格、接口定义、安装要求、测试规范、维护手册 | 受控共享、NDA管控 |
| **Level 3：公开知识资产** | leleby、行业平台、AI采购系统 | 产品语义卡（产品规格、技术参数、适用标准、认证信息、能力标签） | 脱敏审批、双人授权 |

#### 2.5.2 流通目标生态

lookWhy 的知识资产可流通至以下三类外部系统，leleby 是其中重要的战略出口之一：

```
                            外部生态系统
                                 ↑
                                 │
                         知识资产交换层
                                 │
         ┌───────────────────────┼───────────────────────┐
         │                       │                       │
      leleby              企业其他系统              本地知识工具
         │                       │                       │
   AI采购平台              PLM/PDM/MES             Obsidian
   供应链平台              ERP/QMS                 Logseq
   产品语义市场             AI工程助手              企业门户
```

### 2.6 知识流动策略（概念框架）

本系统在设计理念上借鉴 Boisot I-Space 知识流动框架的核心思想，指导知识在系统内部及对外流通策略：

| 知识特性 | lookWhy 策略 |
|---------|-------------|
| **公共编码知识**（已结构化、可公开） | 脱敏后输出至 leleby，形成产品语义资产 |
| **专有编码知识**（已结构化、企业私有） | 严格密级管控，仅内部授权人员可访问 |
| **个人隐性知识**（存在于专家头脑中） | 通过访谈记录、设计决策录入机制引导显性化 |
| **团队隐性知识**（存在于协作过程中） | 通过项目复盘、经验案例模块沉淀为结构化的经验知识 |

该框架用于指导产品的知识采集策略和对外流通边界设计，不直接作为系统的分类模型或数据模型。

### 2.7 与标准制定组织的双向关系

lookWhy 与标准制定组织之间形成双向赋能关系，该关系在生态战略层面统一定义：

| 方向 | 内容 | 说明 |
|------|------|------|
| **标准输入 lookWhy** | 标准组织发布的新标准通过标准更新监测接口进入 lookWhy | 确保企业知识资产基于最新标准 |
| **lookWhy 输出标准组织** | 经脱敏的行业最佳实践、知识图谱可支撑标准草案编制 | 使标准制定基于真实数据 |

标准组织的分类体系可作为系统分类框架的参考来源。该功能的战略优先级在第三阶段（知识资产流通与生态协同）中体现。

### 2.8 与AI生态的关系

在AI应用生态中，lookWhy 承担**工程AI**的角色，与 leleby 的**商业AI**角色形成互补：

| 维度 | lookWhy AI 服务 | leleby AI 服务 |
|------|----------------|----------------|
| **服务对象** | 企业工程师 | 采购Agent/企业采购 |
| **接口协议** | MCP（模型上下文协议） | HTTP / JSON-LD / MCP |
| **数据范围** | Level 1 完整知识 | Level 3 公开语义资产 |
| **典型场景** | "这个设计为什么这样？" | "哪些产品满足这个采购需求？" |

两个系统的AI接口共享同一套语义基础设施（本体、分类框架）。


## 3. 用户群体与业务场景

### 3.1 主要用户角色

| 角色 | 职责 |
|------|------|
| **产品设计工程师** | 检索设计依据、标准和经验；记录设计决策原因；引用知识原子指导产品开发 |
| **工艺工程师** | 管理工艺参数来源、验证过程及变更原因；沉淀制造经验 |
| **标准化工程师** | 管理企业标准及引用的国标/行标；处理标准换版影响分析；维护标准与产品的关联关系 |
| **质量/合规工程师** | 追溯合规证据链；生成符合性报告；管理验证计划与证据包 |
| **知识管理员** | 审核AI抽取结果；维护分类标签体系；管理知识生命周期状态 |
| **本体工程师** | 维护语义关系模型，管理本体版本演进，确保与 leleby 语义层对齐 |
| **行业标准编制专家** | 基于脱敏行业知识编制团体/行业标准草案 |

### 3.2 核心应用场景

- **新型号研发**：系统自动匹配现行有效标准版本，推送相关设计知识与经验
- **老型号维护**：系统锁定该型号指定的标准版本，确保技术状态一致性
- **设计决策记录**：工程师将"为什么这样设计"的结构化依据录入系统
- **合规证据管理**：从标准要求到测试报告的完整证据链归档与审计
- **标准换版影响分析**：新标准发布时，自动识别受影响的产品型号与知识原子
- **知识经验库建设**：失败案例、设计禁忌、最佳实践的系统化沉淀与复用
- **企业/团体标准编制**：基于知识图谱的结构化标准草案生成
- **知识资产对外输出**：将产品语义资产安全输出至 leleby 或合作伙伴系统


## 4. 核心理念

### 4.1 从文件驱动到知识驱动

- **传统模式**：标准文件 → 人工理解 → 工程设计 → 人工验证
- **lookWhy模式**：标准语义知识 → 计算机理解 → 智能辅助设计 → 自动符合性验证

知识不再是静态文档，而是可被系统理解、推理和执行的动态资产。

### 4.2 知识原子是核心资产

将文档解构为独立、可计算、可关联的最小知识单元。每个原子必须：

- 附着于具体的文件版本和物理锚点（确保可溯源）
- 具备独立的业务价值（可脱离原文被理解和使用）
- 承载完整的元数据（来源、密级、权威分、适用上下文等）

知识原子的类型包括但不限于：

| 原子类型 | 说明 | 示例 |
|---------|------|------|
| **规则（Rule）** | 条件-结论形式的指导性知识 | "当壁厚≥5mm时，预热温度≥100℃" |
| **陈述（Statement）** | 事实性描述 | "材料X的屈服强度为355MPa" |
| **判断（Judgment）** | 价值/适用性判定 | "该公差适用于精密配合面" |
| **公理/公式（Axiom/Formula）** | 基础原理与计算公式 | "σ = F/S" |
| **决策（Decision）** | 设计/工艺方案选择及原因 | "选择8极12槽以降低齿槽转矩" |
| **约束（Constraint）** | 设计边界条件 | "最高工作温度不超过85℃" |
| **经验（Experience）** | 最佳实践与教训 | "不建议采用X结构，历史失效率高" |
| **模式（Pattern）** | 可复用的解决方案模板 | "高速轴承选型模式" |

系统支持原子类型的动态扩展，企业在实施时可自定义新增类型。

### 4.3 知识谱系决定可信度

严格区分两种知识生成类型：

- **原始知识（Primary）** ：直接从源文件提取，未经加工
- **衍生知识（Derived）** ：基于一条或多条已有知识推断产生

衍生知识必须记录 `derived_from` 父级指针，确保推论可验证、可回退。界面必须对衍生知识进行视觉差异标识，其检索排序默认低于原始知识。

### 4.4 标准管理依赖上下文

不采用全局统一的"有效/过期"二元状态。引入三重生命周期状态：

- **现行有效**：最新发布版本，适用于新型号设计
- **指定维持（专用有效）** ：已被替代但仍指定用于特定老型号
- **全局作废**：无任何型号依赖，仅供历史追溯

系统通过"设计上下文"切换（新型号研发/特定型号维护/全局管理）实现新老产品标准的精准匹配。

### 4.5 工业知识资产化路径

企业研发制造过程产生数据 → lookWhy 沉淀为私有知识资产 → 行业共性知识脱敏汇聚 → 授权发布至 leleby 等外部平台。知识随业务流动而持续增值。

### 4.6 知识分类是视图，知识图谱是本底

lookWhy 的核心设计原则是底层逻辑与表层呈现的分离：

- **底层表达**：所有知识以**知识图谱/本体模型**（Knowledge Graph / Ontology）为核心组织方式。知识原子是图中的节点，语义关系（如 `belongsTo`、`derivedFrom`、`appliesTo`、`verifiedBy`、`usedIn`）通过图的边表达，形成多维语义网络。
- **表层呈现**：传统知识分类体系（如按业务领域、产品、组织部门、生命周期分类）作为**可配置的管理视图和导航维度**存在，供不同角色在不同场景下使用。
- **切换灵活性**：用户可在多种视图间切换，切换不改变图谱底层结构。多个分类维度可同时作用于同一知识原子（如一条绕线优化经验可同时归属"工艺知识"、"电机产品"、"降噪设计"三个分类维度）。
- **知识类型兼容**：系统同时支持**陈述性知识**（Declarative Knowledge，原子类型为"陈述"和"公理/公式"，表达"是什么"）和**程序性知识**（Procedural Knowledge，原子类型为"规则"、"判断"、"决策"、"经验"、"约束"和"模式"，表达"怎么做"和"如何判断"），二者在原子类型层面已有区分，在分类视图中可进一步加标签。


## 5. 知识体系架构

### 5.1 知识组织原则（前置说明）

四层知识模型描述的是知识的**成熟度与抽象层次**（从公共基础知识到具体项目实例），而非知识的**存放位置**。在每一层内部，知识均以**知识图谱**形式组织：每个知识原子是图中的一个节点，原子之间的语义关系通过图的边表达。

传统分类体系（如产品维度、部门维度、生命周期维度）在系统实现中作为**图谱之上的可配置视图**：系统不要求知识原子归属于唯一的树状分类节点，而是支持一个原子同时带有多个分类维度的标签；用户切换视图时，系统根据标签过滤展示不同的原子子集，图谱底层结构和语义关系保持不变。

### 5.2 四层知识模型

lookWhy 采用四层知识模型组织知识，该分层也作为与 leleby 进行语义层面对齐和交换范围的参照依据：

| 层级 | 名称 | 内容说明 | 是否可与leleby共享 |
|------|------|----------|-------------------|
| **第1层** | **公共基础知识层** | 物理单位、数学公式、基础材料属性、通用几何、工程常识 | 本体共享，实例视授权范围 |
| **第2层** | **行业领域知识层** | 行业标准规范、通用产品结构、行业术语；来源包括ISO/IEC/GB等公开标准及行业脱敏数据 | 本体共享，实例视授权范围 |
| **第3层** | **企业私有知识层** | 企业内部标准、产品设计规范、工艺参数、材料选型规则、专利解读、设计经验、失效案例 | **严禁自动流出**，仅输出经脱敏抽象的产品语义卡 |
| **第4层** | **项目/型号知识层** | 特定型号产品的设计记录、测试报告、问题归零报告、生产数据 | **严禁自动流出**，属于企业最核心机密 |

### 5.3 分类与视图机制

#### 5.3.1 分类视图定义

分类视图是一组可配置的分类标签体系，用于面向不同用户角色和使用场景提供知识导航。系统的分类框架与《leleby & lookWhy 工业知识与语义生态战略规划 v0.2》第6章定义的工业分类框架保持一致，包含行业分类、产品分类、技术分类、应用领域分类、功能能力分类、知识领域分类六个维度。

系统预置以下分类视图，并支持企业自定义扩展：

| 视图名称 | 说明 | 参考来源 |
|---------|------|----------|
| **业务领域视图** | 按知识所属业务领域分类：研发设计、工艺制造、质量合规、市场服务等 | 企业通用实践 |
| **知识类型视图** | 按知识形态分类：标准规范、设计方案、工艺规程、检验方法、经验案例等 | GB/T 23703.7 |
| **产品维度视图** | 按产品/产品系列分类：电机类、电池类、传感器类等 | 企业产品谱系 |
| **组织维度视图** | 按部门/团队分类：研发部、工艺部、质量部等 | 企业组织架构 |
| **生命周期视图** | 按知识成熟度分类：草案、已审核、有效、已归档、已弃用 | 知识生命周期管理 |
| **知识资产类型视图** | 按知识内容类别分类：标准知识、产品知识、工艺知识、工程经验、专利知识、合规知识 | lookWhy 知识资产定义 |

每个分类视图本质是一套树状或网状标签体系。一个知识原子可以同时被多个视图中的多个标签标记。

#### 5.3.2 视图与图谱的关系

- **视图不存储数据**：分类标签作为知识原子的元数据属性存储，但不影响原子之间的图谱关系
- **检索时可组合视图**：用户可同时选择多个视图的多个标签进行组合过滤（如"研发领域 + 电机产品 + 有效状态"）
- **切换视图不影响底层**：从"部门视图"切换到"产品视图"，展示的原子集合改变，但原子间的语义关系（如 `derivedFrom`、`appliesTo`）保持不变
- **默认视图可配置**：不同角色（如设计工程师 vs. 质量工程师）可设置不同的默认视图

#### 5.3.3 与 GB/T 23703.7 的映射关系

系统将 GB/T 23703.7-2014 中定义的知识分类维度作为**推荐默认视图模板**，企业可按需裁剪或扩展。系统不强制要求知识归属单一分类节点，而是支持多维度柔性标记，从而兼容标准要求的同时满足知识图谱的灵活性。

### 5.4 知识资产类型

系统管理以下知识资产类型，这些类型跨越全部四个层级：

| 资产类型 | 说明 | 示例 |
|---------|------|------|
| **标准知识** | 国家标准、行业标准、企业标准的结构化语义表示 | IEC 60034 结构化条款与要求 |
| **产品知识** | 产品分类、结构组成、技术参数、产品型号谱系 | BLDC电机产品结构树 |
| **工艺知识** | 制造工艺路线、工艺参数、设备要求、工装夹具 | 绕线工艺参数及依据 |
| **工程经验** | 设计准则、最佳实践、失败案例、设计禁忌 | "高速轴承应选用陶瓷球" |
| **专利知识** | 专利技术方案解读、技术能力标签、适用产品范围 | 低噪声结构专利 → 低噪声设计能力 |
| **合规知识** | 法规要求、符合性判定规则、验证方法、证据模板 | 欧盟RoHS符合性证据链模板 |


## 6. 核心功能需求

### 6.1 知识采集与录入

#### 6.1.1 多格式文档上传
系统支持 PDF、DOC/DOCX、XLS/XLSX、PPT/PPTX、TXT、MD、HTML、XML、扫描件等格式的批量上传与自动元数据解析。

#### 6.1.2 手动录入
支持单文档手动填写元数据，支持在线预览与编辑。

#### 6.1.3 语音录入
支持语音输入转文字，先存草稿，复核后入库。

#### 6.1.4 双轨知识提取
系统提供两种知识提取模式：

- **AI智能提取模式**：调用大模型自动识别原子类型、生成摘要、推荐分类标签与语义关系。提取结果存入"待审核区"，经人工确认后方可正式入库。
- **人工录入模式**：不调用AI，通过表单或结构化模板（Excel/CSV）批量导入原子。

两种模式输出统一的知识原子格式，确保下游使用无差异。当AI服务不可用时，系统自动降级至人工模式。

### 6.2 知识建模与结构化

#### 6.2.1 知识原子建模
系统支持将文档内容抽取为多种类型的知识原子（规则、陈述、判断、公理/公式、决策、约束、经验、模式）。每个原子须记录摘要、正文、物理锚点、类型、密级、权威分、适用产品谱系、关联标准版本等完整元数据。

#### 6.2.2 语义关系建模
系统支持在知识原子之间建立语义关系，包括但不限于：
- **归属关系**（belongsTo）：原子属于某分类维度或知识资产类型
- **衍生关系**（derivedFrom）：原子由哪些其他原子推导产生
- **适用关系**（appliesTo）：原子适用于哪些产品/工艺/场景
- **验证关系**（verifiedBy）：原子被哪些测试/数据所验证
- **引用关系**（references）：原子引用自哪些标准/文档

#### 6.2.3 原子与文件双向关联
- 从原子可一键跳转至原文锚点位置
- 从原文可查看该文档提取的全部原子列表

#### 6.2.4 知识分类标记
在知识原子建模时，用户可为原子标记多个分类视图的标签（如同时标记"工艺知识"、"电机产品"、"降噪设计"），支持多维度柔性分类，不强制单一树状归属。

### 6.3 知识管理

#### 6.3.1 多维度切片筛选
支持按时段、来源/权威分、密级、覆盖范围、分类视图标签、生命周期状态、生成类型、原子类型进行组合筛选。筛选结果以知识原子列表呈现。

#### 6.3.2 视图切换导航
用户可在不同分类视图（业务领域、产品维度、组织维度、知识类型等）间自由切换，系统根据当前视图调整导航结构。切换视图不改变底层知识图谱数据，仅影响展示维度。

#### 6.3.3 设计上下文切换
系统提供"设计上下文"切换组件：

- **新型号研发模式**：自动过滤"指定维持"的旧版知识，仅展示"现行有效"原子
- **特定型号维护模式**：根据绑定关系匹配该型号指定的标准版本，非适用版本置灰屏蔽
- **全局管理模式**：展示全量数据，供标准化工程师及管理员使用

普通工程师仅可访问被授权的型号上下文（型号准入控制）。

#### 6.3.4 切片批量操作
在筛选结果中支持：

- 批量软删除（标记为"已弃用"，屏蔽有效检索但保留历史）
- 批量硬删除（物理移除，需双重权限校验）
- 批量导出/拷贝（输出为结构化或自然语言格式）
- 打包传递（生成知识包，自动去重并过滤无权限内容）

### 6.4 标准生命周期管理

#### 6.4.1 标准版本状态管理
系统对标准类知识维护三种生命周期状态：现行有效、指定维持（专用有效）、全局作废。

#### 6.4.2 标准换版处理
新标准发布时，旧标准不自动全局作废。系统要求标准化工程师确认旧标准的适用产品型号范围：绑定型号的转为"指定维持"，未绑定的自动转为"全局作废"。

#### 6.4.3 标准引用关系
显式建模标准间的引用关系（规范性引用/资料性引用）。当被引用标准发生版本变更时，系统自动提醒引用方进行复审。

### 6.5 合规追溯管理

系统支持从标准要求到合规结论的完整证据链管理：

- **证据链模型**：标准要求 → 验证计划 → 测试执行 → 测量数据 → 评价规则 → 合规结果 → 证据包
- **证据包要求**：包含测试报告、原始数据文件、设备校准证书、人员资质、时间戳及数字签名，确保可审计、可重现

### 6.6 知识谱系与衍生管理

- **原始知识**：直接从文件提取的知识"根节点"
- **衍生知识**：通过AI推理或人工综合产生的二次知识，必须记录 `derived_from` 父级原子列表
- 衍生知识在界面展示中须有视觉差异标识，检索排序默认低于原始知识
- 引用衍生知识用于正式设计输出时，须经用户二次确认

### 6.7 知识检索与可视化

- 支持全文检索（摘要、正文、元数据）及多维高级检索
- 检索结果根据"设计上下文"自动调整优先级排序
- 支持知识图谱可视化展示（原子关系、谱系链、标准引用网络）
- 支持检索结果收藏与标准更新订阅

### 6.8 知识资产交换能力

lookWhy 提供基于权限控制的**知识资产交换层**，支持将不同粒度、不同密级的知识资产安全输出至外部系统。该交换层是《leleby & lookWhy 工业知识与语义生态战略规划 v0.2》第7章"数据交换与流通机制"在 lookWhy 平台的具体实现。

#### 6.8.1 三级数据粒度输出

| 输出等级 | 目标场景 | 数据内容 | 安全控制 |
|---------|---------|---------|----------|
| **Level 1（完整知识）** | 企业内部系统（PLM/PDM/MES/ERP）、内部AI助手 | 完整知识原子、设计原因、工艺参数、经验案例、测试数据 | 企业内网/零信任认证、角色权限 |
| **Level 2（受控共享）** | 供应商协作平台、客户、联合研发伙伴 | 产品规格、接口定义、安装要求、测试规范、维护手册 | 独立授权审批、NDA关联、有效期控制 |
| **Level 3（公开语义资产）** | leleby、行业平台、AI采购系统 | 产品语义卡（规格、参数、认证、能力标签） | 脱敏校验、双人审批、全程留痕 |

#### 6.8.2 语义资产标准化导出
- 支持将选中的知识资产打包为标准化语义包（Semantic Package）
- 语义包格式兼容 leleby 的语义包规范，同时支持企业自定义扩展
- 导出内容包含：知识实体、语义关系、来源溯源、版本信息、授权范围声明

#### 6.8.3 本地知识工具同步
- 支持将知识包导出为"Markdown + YAML Frontmatter"格式
- 导出的MD文件可直接放入 Obsidian、Logseq 等本地知识工具的仓库中
- 支持增量同步与版本差异识别，避免全量重复导出

#### 6.8.4 数据包导入导出
- 支持知识包（.knw 格式）的完整导入与导出
- 导入时自动校验数据完整性、权限合规性及与现有图谱的冲突检测
- 支持跨 lookWhy 实例的知识包迁移

#### 6.8.5 对外输出安全管控
- 所有对外输出操作须经过脱敏校验引擎检查
- Level 2 及以上数据输出须经过双人审批
- 所有对外输出操作记录独立审计日志，支持防泄露追溯


## 7. 外部系统协同关系

### 7.1 与企业内部系统协同

- 与 PDM/PLM 系统对接，获取产品结构、BOM、设计任务上下文
- 与 MES（制造执行系统）对接，获取工艺执行数据与生产反馈
- 与 QMS（质量管理系统）对接，交换检验标准与质量数据
- 与企业身份认证系统集成（LDAP/SAML/OAuth），实现单点登录与统一权限管理

### 7.2 与法规标准更新源协同

对接国家及行业标准管理部门数据源，自动监测标准状态变更与版本更新。

### 7.3 与 leleby 平台的协同

#### 7.3.1 协同定位
lookWhy 为 leleby 提供高质量的工业语义资产数据源（Level 3 公开语义资产）。二者的协同关系遵循《leleby & lookWhy 工业知识与语义生态战略规划 v0.2》第3章和第4章的定义。

#### 7.3.2 共享语义基础设施
两个平台共用一套公共工业本体（单位、材料、标准结构、要求/验证模型），本体的变更由生态技术委员会统一治理，在两个平台间通过标准化流程同步。

#### 7.3.3 数据交换格式
通过标准化工业语义资产包（Semantic Package）实现数据交换，交换内容符合第 6.8 节所定义的 Level 3 输出规范。

### 7.4 与合作伙伴系统的协同

- 支持与供应商、客户、联合研发伙伴的系统进行受控数据交换（Level 2）
- 提供标准化的 API 接口，支持合作伙伴系统按授权范围查询产品规格、接口定义、测试规范等信息

### 7.5 与AI工程助手的协同

系统通过标准化AI接口（如MCP协议）向企业内部的AI工程助手提供知识服务，支持以下交互场景（Level 1 完整知识）：

- **知识检索**：AI助手传入设计上下文和查询条件，系统返回符合权限的知识原子
- **上下文读取**：AI助手根据原子锚点获取原文局部内容（受权限与水印管控）
- **知识沉淀**：AI助手生成的知识经审核后写入系统草稿区
- **标准比对**：AI助手获取新旧标准版本的结构化差异信息

所有AI接口调用须严格执行用户级权限校验与审计留痕。

### 7.6 与本地知识工具的协同

- 支持将知识资产导出为 Obsidian、Logseq 等工具的兼容格式
- 支持双向同步：本地工具中的知识更新可反向同步至 lookWhy 草稿区（经审核后入库）
- 定位为**知识浏览与快速记录的终端**，企业级治理仍由 lookWhy 承担


## 8. 数据治理原则

### 8.1 知识所有权原则

- lookWhy 中第3层（企业私有知识层）和第4层（项目/型号知识层）的全部数据，所有权归属企业客户，lookWhy 平台不享有任何数据使用权
- 企业客户有权随时导出、迁移或删除其全部知识资产

### 8.2 密级管控原则

- 系统实施五级密级管控（公开/内部/秘密/机密/绝密），机密/绝密级知识访问须经双人审批
- 密级可继承（原子继承自文件）且允许人工覆写，但原子密级不得低于其来源文件密级
- 对外输出语义资产时，密级≥秘密的知识自动拦截，须经脱敏审批后方可输出

### 8.3 知识质量治理原则

- AI提取结果须经人工确认方可正式入库
- 知识原子须包含完整的来源元数据（文件溯源、物理锚点、提取方式、审核记录）
- 定期知识审核与过期清理机制
- 衍生知识须验证其父级知识的有效性

### 8.4 谱系完整性原则

- 所有衍生知识必须建立完整的向上追溯链（`derived_from` 指针）
- 删除或弃用任一知识时，系统须检查并提示所有依赖它的衍生知识

### 8.5 对外流通安全原则

- 所有对外输出须经过独立的脱敏校验引擎
- 三级输出粒度（Level 1/2/3）对应不同的审批流程与安全控制
- 输出内容须符合第6.8节的范围限定
- 对外输出操作须支持远程撤回（Revoke）和版本失效管理

### 8.6 审计可追溯原则

- 所有关键操作（查阅、下载、审批、删除、导出、对外输出）记录完整审计日志
- 审计日志至少包含：操作人、操作时间、操作类型、操作对象、操作结果

### 8.7 分类治理与本体治理分离原则

系统将分类标签治理与语义本体治理明确分离，由不同角色维护。该原则与生态战略中"分类治理与本体治理分离"（《leleby & lookWhy 工业知识与语义生态战略规划 v0.2》第9.2节）保持一致：

| 治理维度 | 管理对象 | 负责角色 | 变更影响范围 |
|---------|---------|---------|-------------|
| **分类治理** | 分类视图标签体系（如产品分类、业务领域分类、知识类型分类等） | 知识管理员 | 仅影响检索导航视图，不影响图谱底层结构和语义关系 |
| **本体治理** | 语义关系模型（原子类型、关系类型、本体层次结构） | 本体工程师 | 影响知识图谱表达能力，须通过生态技术委员会与leleby语义层同步评审 |

分类标签的增删改（如新增一个产品分类节点）不影响任何知识原子的语义关系，仅影响该原子在检索视图中的展示位置。语义关系的调整（如新增一种关系类型）须经过生态技术委员会技术评审并同步至公共语义层，确保与 leleby 的语义对齐。

### 8.8 本体与共享语义治理参与原则

lookWhy 作为工业语义基础设施的共建方，须参与生态技术委员会的治理活动：

- lookWhy 本体工程师须参与核心本体变更的技术评审
- lookWhy 平台须按生态战略定义的同步周期接收共享语义更新
- lookWhy 在核心本体基础上的应用层扩展须向生态技术委员会备案


## 9. 发展路线图

### 9.1 第一阶段（MVP）：知识资产形成与治理

- 多格式文档批量上传与元数据解析
- 双轨知识提取（AI + 人工）及审核流程
- 知识原子建模（基础类型：规则、陈述、判断、公理/公式）与多维筛选
- 预置分类视图框架（参考 GB/T 23703.7）
- 设计上下文切换（新型号/老型号）
- 标准版本生命周期管理
- 基础语义检索

### 9.2 第二阶段：知识谱系与合规追溯

- 衍生知识生成与谱系可视化
- 原子类型扩展（决策、约束、经验、模式）
- 合规验证计划及证据链管理
- 与 PDM/PLM/MES/QMS 系统深度集成
- AI工程助手接口上线（Level 1 完整知识输出）

### 9.3 第三阶段：知识资产流通与生态协同

- 三级数据粒度输出机制
- 语义资产输出审批工作流与自动脱敏校验引擎
- 与 leleby 语义包标准对接（Level 3 公开语义资产）
- 与合作伙伴系统的受控数据交换（Level 2）
- 本地知识工具（Obsidian、Logseq）同步能力
- 企业/团体标准编制辅助工具（含标准组织双向数据交换）

### 9.4 第四阶段：行业知识网络

- 多租户行业版部署
- 跨企业知识联邦查询（保持数据隔离）
- 基于知识图谱的生成式AI工程助手全面应用
- 行业标准知识库的持续积累与自动更新
- 参与生态技术委员会的共享语义治理活动
