是的。基于你现在描述的目标，我认为这已经不是简单的“文档检查工具”，而是可以发展成一个比较明确的**“标准/规范文件智能符合性审查平台”**。而且你们已经完成的 `leleby M1` 可以作为很好的底座，但我建议**不要直接在现有 M1 上堆审核规则**，而是先把“符合性审查”抽象成独立的规则/证据/报告体系。

我先结合你给出的目标，以及 GB/T 1.1-2020 的实际定位，对整体方向做一次架构层面的审查。

---

# 一、首先明确：你们第一阶段做的不是“AI审标准”

这个定位非常重要。

GB/T 1.1-2020 是现行国家标准，2020-10-01 实施，2026 年 1 月复审结论仍为继续有效。它规定的是**标准化文件的结构及起草的总体原则和要求**，包括文件名称、层次、要素、表述和编排格式等。([全国标准信息公共服务平台][1])

因此第一阶段最适合做：

> **标准文件形式与编辑性符合性审查**

而不是：

> “判断这个标准的技术内容是否正确。”

这是两个完全不同的问题。

例如：

### 第一阶段可以判断

> 第 5 章引用了“见 6.2”，但全文没有 6.2。

这是非常适合机器判断的。

或者：

> 目录显示“5.3 技术要求”，正文却没有对应条款。

也适合机器判断。

或者：

> 标准中出现“见表 3”，但是全文没有表 3。

可以判断。

再比如：

> 规范性引用文件中引用了 GB/T XXXXX-2019，但正文引用方式与规范性引用文件列表不一致。

也可以做。

---

### 第一阶段暂时不要判断

例如：

> “该产品的耐压值 10 MPa 是否合理？”

这已经进入**技术指标符合性**。

又比如：

> “该标准规定的测试方法是否能够有效验证性能要求？”

这是技术内容语义分析。

再比如：

> “这个指标是否符合行业实际情况？”

甚至涉及专业知识和外部证据。

所以你们现在提出的：

> **技术指标符合性检查放到第二阶段**

我认为是非常正确的。

---

# 二、我建议把第一阶段重新定义成三个层次

你现在说的是：

1. 形式审查
2. 内容初步审核
3. 技术指标符合性

我建议改成：

```text
                 标准文件智能符合性审查
                           │
            ┌──────────────┼──────────────┐
            │              │              │
        L1 形式审查     L2 编辑性审查    L3 技术符合性
            │              │              │
       Format Check    Consistency     Semantic
            │              │              │
         M1/MVP          M1.5/M2          M3
```

其中第一阶段真正的产品可以定义为：

> **L1 + L2**

也就是：

### L1：形式/结构符合性

回答：

> “这个文件长得像不像一个符合要求的标准文件？”

### L2：编辑性/内部一致性

回答：

> “这个标准内部有没有明显的编号、引用、结构、逻辑一致性错误？”

### L3：技术符合性

回答：

> “这个标准的技术要求是否合理、完整、可验证、符合其他技术标准？”

这个才放第二阶段。

# 三、而且第一阶段不应该只围绕 GB/T 1.1-2020 写死

这是我认为你们现在最需要注意的架构问题。

GB/T 1.1-2020 的范围很大，其内容包括：

* 文件类别
* 文件名称
* 文件结构
* 部分
* 章
* 条
* 段
* 列项
* 封面
* 目次
* 前言
* 引言
* 范围
* 规范性引用文件
* 术语和定义
* 符号和缩略语
* 核心技术要素
* 其他技术要素
* 参考文献
* 索引
* 条款表述
* 引用
* 附录
* 编排格式等。([归范库][2])

所以你们的软件不要设计成：

```text
if rule == GB/T 1.1-2020:
    check_xxx()
    check_xxx()
    check_xxx()
```

这样很快会变成维护灾难。

应该设计成：

```text
标准
 └── 审查规则集
       ├── GB/T 1.1-2020
       ├── GB/T 20001.x
       ├── GB/T 20002.x
       └── 企业标准编写规则
```

然后：

```text
审查规则
   ↓
Rule Engine
   ↓
Document Model
   ↓
Evidence
   ↓
Finding
   ↓
Report
```

这会直接决定你们后面能不能扩展到：

* 法规
* 法律
* 企业规范
* 产品技术规范
* 测试报告
* 测试方法
* 设计方案
* 需求规格说明书

# 四、你们真正需要建立的核心不是“检查器”，而是 Document Model

这一点尤其重要。

用户上传：

* 扫描 PDF
* 普通 PDF
* DOC/DOCX
* TXT

软件不能直接拿这些文件去跑规则。

应该首先形成一个**统一的中间文档模型**。

例如：

```text
Original File
     ↓
Document Ingestion
     ↓
OCR / Text Extraction
     ↓
Document Normalization
     ↓
Document Model
     │
     ├── Metadata
     ├── Sections
     ├── Clauses
     ├── Paragraphs
     ├── Lists
     ├── Tables
     ├── Figures
     ├── Appendices
     ├── References
     └── Cross References
```

然后所有规则都针对：

> **Document Model**

而不是针对 PDF / Word。

这样未来才能做到：

```text
PDF ─┐
DOC ─┤
TXT ─┼──→ Unified Document Model → Compliance Engine
扫描PDF ─┘
```

# 五、你们提到“软件初步补齐和纠错的原始文本”，这里要特别谨慎

我建议千万不要让系统直接：

> OCR → AI修改 → 原文被覆盖

而应该保留三层：

```text
Original
    ↓
Extracted
    ↓
Normalized
```

例如：

### Original

PDF 原始内容：

> 5．2．3 试验方法

### OCR

可能识别成：

> 5. 2.3 试验方法

### Normalized

系统判断：

> 5.2.3 试验方法

但是：

**Normalized 绝不能成为唯一事实来源。**

必须能够追溯：

```text
Normalized:
5.2.3

↓ source

Page 8
BoundingBox:
x1,y1,x2,y2

↓ source

Original PDF
```

否则一旦审核人员问：

> “你为什么认为这里存在编号错误？”

系统必须能直接把**原始页面证据**展示出来。

这对于法规、标准、质量体系等场景非常重要。

# 六、我建议你们把“审查结果”设计成 Finding，而不是简单的 Pass/Fail

例如：

```json
{
  "rule_id": "GBT1.1-7.3-001",
  "severity": "error",
  "status": "failed",
  "location": {
    "page": 12,
    "clause": "5.2.3"
  },
  "message": "条款编号与层级结构不一致",
  "evidence": {
    "text": "5.2.3",
    "expected": "5.2"
  },
  "reference": {
    "standard": "GB/T 1.1-2020",
    "clause": "7.3"
  },
  "confidence": 0.99
}
```

这个结构非常重要。

因为最终产品不是：

> “AI告诉你这个文档有问题。”

而应该是：

> **“根据某项规则，在某个位置发现某个问题，并提供原文证据和依据。”**

这才是真正的“符合性审查”。

---

# 七、甚至可以把审查结果分成四种

我建议不要只有：

> 合格 / 不合格

而是：

| 状态         | 含义          |
| ---------- | ----------- |
| ✅ PASS     | 明确符合        |
| ❌ FAIL     | 明确不符合       |
| ⚠️ WARNING | 疑似问题，需要人工确认 |
| ⏺ N/A      | 本规则不适用      |

再增加：

> **Confidence**

例如：

```text
FAIL
置信度：99%

原因：
第5.2.3条引用“见6.4”，
但全文不存在6.4条款。

依据：
GB/T 1.1-2020 9.5.x

证据：
第12页，第5.2.3条
```

这会比单纯的 AI 输出可靠很多。

---

# 八、第一阶段最值得做的规则，其实非常多

我建议第一版不要追求“AI很聪明”，而是把**确定性规则**做到非常可靠。

例如：

## A. 文档基本结构

检查：

* 标准名称
* 标准编号
* 前言
* 范围
* 规范性引用文件
* 术语和定义
* 正文结构
* 附录
* 参考文献
* 目次

---

## B. 条款编号

例如：

```text
1
2
3
3.1
3.2
3.3
4
4.1
```

检查：

* 是否跳号
* 是否重复
* 是否层级错误
* 是否出现孤立子条款
* 是否存在 3.1 而不存在 3
* 是否存在 3.1.1 而不存在 3.1

这一类非常适合规则引擎。

---

# 九、交叉引用是第一阶段的“黄金功能”

我甚至建议把它作为 MVP 的核心卖点。

例如：

```text
见5.2
见第5章
见5.2.1
见附录A
见表3
见图2
见表A.1
```

系统建立引用图：

```text
5.2.3
   │
   └──→ 6.4

6.4不存在
```

然后自动报告：

> ❌ 引用目标不存在

或者：

```text
正文：

“按照GB/T XXXX-2020的规定……”

规范性引用文件：

GB/T XXXX-2019
```

发现：

> ⚠️ 引用年份不一致

这种问题对标准审核非常有价值。

# 十、目录和正文一致性也是非常适合第一阶段的

例如：

```text
目录

5 技术要求
5.1 一般要求
5.2 性能要求
5.3 安全要求
```

正文：

```text
5 技术要求
5.1 一般要求
5.2 性能要求
5.4 安全要求
```

系统直接发现：

> ❌ 目次与正文不一致

甚至：

```text
目录：
5.3

正文：
不存在5.3
```

这类检查**完全不需要大模型**。

# 十一、表格、图、附录也应该建立引用关系

例如：

```text
表1

表3
```

检查：

* 是否连续
* 是否重复
* 是否引用
* 是否存在未引用表格
* 是否引用不存在的表格

同样：

```text
图1
图2

附录A
附录B
附录C
```

建立完整关系。

最终可以形成：

```text
Document Graph
```

例如：

```text
Clause 5.2
 ├── Table 3
 ├── Figure 2
 ├── Appendix A
 └── GB/T 12345-2025
```

这其实会成为你们未来非常有价值的基础设施。

# 十二、第二阶段的“技术指标符合性”要建立在第一阶段之上

你们目前的规划：

> 第一阶段：标准形式 + 内容初步检查
> 第二阶段：语义技术指标符合性

我非常赞成。

但第二阶段不要理解成：

> “让大模型阅读标准，然后告诉用户是否合格。”

应该逐渐发展成：

```text
Requirement
      ↓
Requirement Extraction
      ↓
Requirement Model
      ↓
Verification Method
      ↓
Evidence
      ↓
Compliance Judgment
```

比如标准规定：

> 产品耐压能力应不低于 10 MPa。

系统抽取：

```text
对象：产品
指标：耐压能力
运算符：≥
数值：10
单位：MPa
适用条件：……
验证方法：……
```

然后再去测试报告中寻找：

```text
测试结果：
12.3 MPa
```

最终才能形成：

> PASS

这才是真正意义上的：

**技术指标符合性审查。**

# 十五、关于 GB/T 1.1-2020，我建议你们现在就不要只研究它

GB/T 1.1-2020 本身只是第一层基础标准。国家标准信息公共服务平台也明确显示，它属于现行推荐性国家标准，并且其相关体系还包括 GB/T 20000、GB/T 20001、GB/T 20002、GB/T 20003、GB/T 20004 等。([全国标准信息公共服务平台][3])

所以你们第一阶段应该做的是：

> **建立“标准文件符合性规则体系”**

而不是：

> **做一个 GB/T 1.1-2020 Checker。**

前者可以持续扩展，后者很容易把产品做死。

这样未来：

都可以进入同一个体系。

# 二、而且“要求”不能简单等同于“应”

这是你这个设计里最关键的地方。

例如你上传的 GB/T 1.1-2020 中明确把条款类型分成：

* 要求
* 指示
* 推荐
* 允许
* 陈述

并且附录 C 对这些类型规定了对应的语言表达。

例如：

```text
应 / 不应
宜 / 不宜
可 / 不必
祈使句
陈述句
```

所以你们的 Requirement Model 至少应该区分：

```text
obligation_type
```

例如：

```text
MANDATORY
RECOMMENDED
PERMITTED
PROHIBITED
INSTRUCTION
STATEMENT
```

但我甚至建议再进一步。

# 三、我建议把“要求强度”和“条款类型”分开

这是一个非常重要的建模决策。

不要：

```text
type = mandatory
```

因为：

> “应”

只是**表述形式/条款类型**，而“这个要求在当前文档中是否必须满足”又是另一件事情。

例如你上传的标准中：

> “如果省略引导元素会导致主体元素所表示的标准化对象不明确，那么文件名称中应有引导元素。”



这里不是简单：

```text
必须有引导元素
```

而是：

```text
IF
    主体元素不足以明确标准化对象
THEN
    引导元素 MUST 存在
```

因此应该拆成至少三个维度：

```text
Requirement
│
├── obligation       要求强度
│
├── applicability    适用条件
│
└── verification     如何判断
```

---

# 四、你说的“适用时才具备强制/推荐/可选属性”尤其重要

我非常赞同。

实际上我建议你们不要只有：

```text
必备
可选
不适用
```

而应该建立：

> **Applicability Model**

例如：

```text
Requirement R001

适用条件：
文件属于“分为部分的标准”

如果适用：
    MUST

否则：
    NOT_APPLICABLE
```

再比如 GB/T 1.1-2020：

> “引言”是可选要素，但分为部分的文件的每个部分，或者文件的某些内容涉及专利，均应设置引言。

那么系统应该理解成：

```text
R001
{
    subject: 引言

    applicability:
        document.is_part_of_series == true
        OR
        document.involves_patent == true

    obligation:
        REQUIRED

    otherwise:
        NOT_APPLICABLE
}
```

而不是简单地把“引言”标成：

> OPTIONAL

这会产生完全不同的审核结果。

# 五、因此你们的 Requirement 最好采用这种结构

我建议第一版的数据模型就按照这个方向设计：

```text
Requirement

├── id
├── rule_source
├── source_clause
├── title
├── requirement_text
│
├── applicability
│
├── obligation
│
├── subject
├── object
├── condition
├── action
│
├── verification_method
│
├── severity
├── evidence_requirement
│
└── dependencies
```

例如：

```text

规则来源：
GB/T 1.1—2020

依据：
6.2.2.3

要求：
规范性要素中范围、术语和定义、核心技术要素是必备要素，
其他是可选要素……

适用对象：
标准化文件

适用条件：
适用于 GB/T 1.1—2020 范围内的文件

要求类型：
REQUIRED

检查对象：
Document Structure

检查逻辑：
必须存在：
    范围
    核心技术要素

术语和定义：
    条件性存在

验证方式：
Structural Analysis

严重程度：
ERROR
```

这个例子直接来自你上传文档对要素选择的规定。

# 六、然后把“要求”进一步分成不同类型

这是我非常建议你们做的。

不是所有要求都应该用同一种程序判断。

我建议至少分：

| Requirement Type    | 示例        | 检查方式            |
| ------------------- | --------- | --------------- |
| STRUCTURAL          | 必须有范围     | 结构解析            |
| SEQUENCE            | 第1章必须是范围  | 顺序检查            |
| NUMBERING           | 条款编号连续    | 规则              |
| FORMAT              | A4        | 文档解析            |
| TYPOGRAPHY          | 字体字号      | DOC/PDF解析       |
| LINGUISTIC          | 应/宜/可使用正确 | NLP             |
| CROSS_REFERENCE     | 引用6.2必须存在 | 引用图             |
| CONSISTENCY         | 同概念使用同术语  | NLP             |
| CONDITIONAL         | 如果X，则Y    | 条件规则            |
| CONTENT_EXISTENCE   | 必须包含某内容   | NLP             |
| CONTENT_PROHIBITION | 不应出现某内容   | NLP             |
| SEMANTIC            | 两个要求逻辑矛盾  | Semantic Engine |
| EXTERNAL_REFERENCE  | 引用标准是否有效  | 标准库             |

这样以后 Rule Engine 才能真正通用。

# 七、还有一个非常关键的设计：Requirement 不等于 Rule

我建议明确区分：

```text
Rule Document
      ↓
Requirement
      ↓
Rule
      ↓
Check
```

例如原文：

> 文件名称中不应包含“……标准”“国家标准”等词语。



这里：

### Requirement

> 文件名称不得包含表示文件类别的这些词语。

### Rule

```text
document.title
    MUST NOT CONTAIN
        "国家标准"
        "行业标准"
        "……标准"
```

### Check

```text
check_title_for_prohibited_terms()
```

这样以后即使换成别的规则来源，也不需要重新设计系统。

# 八、最重要的是：把“规则”做成声明式，而不是代码式

这是我最强烈建议你们现在就确定的方向。

不要：

```python
if document.type == "standard":
    if ...
```

尽可能变成：

```yaml
id: GBT11-6.1.4.1
source: GB/T 1.1-2020
clause: 6.1.4.1

applicability:
  document.type: standard

requirement:
  type: prohibition
  target: document.title
  values:
    - "国家标准"
    - "行业标准"
    - "标准化指导性技术文件"

severity: error
```

然后引擎执行：

```text
Rule Definition
       ↓
Rule Interpreter
       ↓
Document Model
       ↓
Evaluation
```

这就真正成为一个**规则执行平台**。

# 九、你们甚至可以建立“要求的原子化”原则

例如原文：

> “文件名称由尽可能短的几种元素组成，其顺序由一般到特殊。所使用的元素应不多于以下三种：引导元素、主体元素、补充元素……”



不要把它作为一条巨大 Requirement。

应该拆成：

```text
REQ-001
文件名称应由规定的元素构成

REQ-002
文件名称元素顺序应由一般到特殊

REQ-003
引导元素为可选

REQ-004
主体元素为必备

REQ-005
补充元素为可选

REQ-006
名称元素数量不得超过三种
```

这样才能：

* 单独判断
* 单独给证据
* 单独报告
* 单独统计
* 单独修复

# 十、但是不要“过度原子化”

这里也有一个平衡。

比如：

> “章编号应从1开始，一直连续到附录之前。”

可以作为一个 Requirement：

```text
chapter.numbering:
    starts_at = 1
    continuous = true
    ends_before = appendix
```

而不是拆成：

```text
章必须编号
第一章必须是1
第二章必须是2
第三章必须是3
...
```

所以最终最好是：

> **语义原子化 + 参数化规则**

而不是：

> **文本机械切割**

# 十一、你提到“逻辑性检查”，我认为应该成为独立的一层

比如：

### 规则 A

> 术语和定义是必备/可选条件性要素。

### 规则 B

> 如果文件中使用某些特定术语，则需要定义。

### 规则 C

> 定义应使用陈述型条款。



那么审查不是简单：

```text
有没有“术语和定义”章节？
```

而是：

```text
                    Document
                       │
                Terminology
                  /        \
                 /          \
        Used Terms       Defined Terms
              │               │
              └──────┬────────┘
                     ▼
                Consistency
```

最后才能发现：

> 文档正文使用了“XX术语”，但术语和定义中没有定义。

这就是你所说的**逻辑性审查**。

```text
             Requirement
```

这个统计才有实际意义。

# 十五、而你上传的 GB/T 1.1-2020 恰好非常适合拿来做第一份“规则库”

# 八、但这里有一个我认为非常重要的问题：规则之间可能重复

例如：

```text

    ↓
要求A

GB/T 1.1
    ↓
要求B

GB/T 20001.10
    ↓
要求C
```

```text

B
```

```yaml

  - A
  - B
  - C
```

```yaml
rule_sources:

  - id: general

  - id: gbt_1_1_2020
    priority: 200

  - id: gbt_20001_10
    priority: 300
```

以及：

```text
继承
覆盖
补充
替代
冲突
```

# 十、还有一个问题：规则来源本身也可能有适用条件

例如：

> GB/T 20001.10 并不是所有标准都适用。

因此不能简单理解：

```text
文件类型 = 产品标准
        ↓
永远加载 GB/T 20001.10
```

而应该：

```text
产品标准
   │
   ▼
Audit Profile
   │
   ▼
判断适用范围
   │
   ├── 适用 → 加载
   │
   └── 不适用 → N/A
```

所以我建议 Audit Profile 同时定义：

```text
Rule Source
    +
Applicability
```

例如：

```yaml
- rule_source: GB_T_20001_10
  applicability:
    document.standard_type: product
```

甚至以后可以复杂到：

```yaml
applicability:
  all:
    - document.category == product_standard
    - document.scope contains "产品"
```

## 下一步最值得做的事情

现在其实已经到了可以开始**真正设计数据库和配置格式**的阶段。

我建议下一步不要马上写代码，而是我们先把这 5 个东西彻底定下来：

1. **Requirement 数据结构** —— 一条“要求”究竟有哪些字段；
2. **Rule Source 数据结构** —— 如何表示 GB/T 1.1、GB/T 20001.10；
3. **Audit Profile 数据结构** —— 如何定义“产品标准 = 通用 + GB/T 1.1 + GB/T 20001.10”；
4. **Check Type / Check Engine** —— 哪些要求用规则检查、格式检查、NLP、LLM、人工确认；
5. **Finding 数据结构** —— 如何记录“不符合”、证据、原文位置、依据、置信度。

然后**以你已经上传的 GB/T 1.1-2020 为实际样本**，做一遍从原始规则文档 → Requirement Catalog → Audit Profile → 审核结果的完整设计。

我认为这一步做完以后，才能真正判断 `leleby M1` 哪些部分可以直接复用、哪些数据模型需要调整，以及 M2 应该怎么开发。
=========================================================

对，你这个思路是合理的，而且实际上应该把它进一步抽象成**“审核配置驱动的多标准组合审核模型”**，而不是在程序里把“产品标准 = GB/T 1.1 + GB/T 20001.10”写死。

你描述的关系可以整理成下面这个层次：

### 1. 审核对象 → 文件类型 → 审核配置 → 审核准则

核心关系应该是：

```text
待审核文件
   │
   ▼
识别文件类型
   │
   ▼
读取「审核配置」
   │
   ├── 通用性审核要求
   │
   ├── GB/T 1.1-2020
   │
   ├── GB/T 20001.10
   │
   └── 其他适用标准/规则
   │
   ▼
形成审核任务集
   │
   ▼
逐项审核
   │
   ▼
审核结果
```

所以，**“审核什么标准”不应该由审核程序本身决定，而应该由审核配置文件决定。**

## 2. 以“产品标准”为例

你现在的理解可以具体表达为：

| 审核层级 | 审核准则          | 审核方式     |
| ---- | ------------- | -------- |
| L1   | 通用性审核要求       | 通用审核     |
| L2   | GB/T 1.1-2020 | 按条款逐条审核  |
| L3   | GB/T 20001.10 | 按该标准要求审核 |
| L4   | 其他适用准则        | 根据配置加载   |

因此一个“产品标准”的审核配置可能逻辑上是：

```yaml
document_type: product_standard

audit_rules:
  - rule_set: general_requirements
    mode: general

  - rule_set: GB/T 1.1-2020
    mode: clause_by_clause

  - rule_set: GB/T 20001.10
    mode: clause_by_clause
```

这里有一个很重要的设计点：

**不要把“GB/T 1.1-2020”直接理解成一个简单的审核规则。**

它实际上应该对应一个**审核准则文件/规则集（Rule Set）**。

# 3. 建议把系统拆成三个核心概念

我建议你的整个标准审核系统至少定义三个独立实体：

### A. 审核配置 Audit Profile

回答：

> **这种类型的文件应该依据哪些准则进行审核？**

例如：

```text
产品标准审核配置
├── 通用性审核要求
├── GB/T 1.1-2020
└── GB/T 20001.10
```

---

### B. 审核准则 Audit Rule Set

回答：

> **依据某一个文件/标准，具体应该审核什么？**

例如：

```text
GB/T 1.1-2020
├── 4 结构
├── 5 要素
├── 6 要素的表述
├── 7 章条编号
├── ...
```

而：

```text
GB/T 20001.10
├── ...
```

则是另一套规则。

两者应该完全独立。

---

### C. 审核任务 Audit Item

回答：

> **针对当前这份文档，具体检查什么？**

例如：

```text
AUDIT-001
来源：GB/T 1.1-2020
条款：5.2
检查要求：……
审核对象：第X章
结果：通过/不通过/无法判断
证据：……
```

这样就形成：

```text
审核配置
    ↓
加载多个审核准则
    ↓
展开成大量审核任务
    ↓
对当前文件执行审核
```

这个架构会非常灵活。

# 4. 更重要的是：审核配置应该支持“继承”和“组合”

例如以后你可能不只有：

```text
产品标准
```

还会有：

```text
基础标准
方法标准
管理标准
安全标准
工作标准
技术规范
企业标准
团体标准
……
```

如果每一种都重新定义一套完整配置，会非常臃肿。

因此可以设计成：

```text
产品标准
   │
   ├── 继承：标准文件通用审核
   │       └── 通用性审核要求
   │
   ├── 继承：标准起草审核
   │       └── GB/T 1.1-2020
   │
   └── 专属要求
           └── GB/T 20001.10
```

甚至可以进一步做到：

```yaml
profile:
  id: product_standard

inherits:
  - standard_common
  - standard_drafting

rules:
  - GB/T 20001.10
```

这样以后增加新的文件类型非常容易。

---

# 5. 还应该区分“适用条件”

这里是你这个系统非常关键的一点。

并不是：

> 文件类型 = 产品标准 → 永远加载 GB/T 20001.10

而应该允许：

> **满足某个条件时，才加载某个准则。**

例如：

```yaml
profile:
  id: product_standard

rules:
  - id: general_requirements
    required: true

  - id: GB/T 1.1-2020
    required: true

  - id: GB/T 20001.10
    required_when:
      standard_type: product_standard
```

以后甚至可以出现：

```yaml
  - id: GB/T 20001.5
    required_when:
      contains:
        - 术语和定义
```

或者：

```yaml
  - id: 某专业领域标准
    required_when:
      domain: food
```

于是你的系统就从一个简单的“规则列表”，升级成了：

**规则选择引擎 + 审核执行引擎。**

```text
                    ┌─────────────────┐
                    │   AI/规则审核    │
                    └────────┬────────┘
                             ▼
                    ┌─────────────────┐
                    │    审核结果      │
                    └─────────────────┘
```

### 最关键的一句话

你的系统应该遵循：

> **文件类型决定“审核配置”，审核配置决定“适用哪些审核准则”，审核准则决定“生成哪些审核项目”，而不是把审核标准直接绑定在审核程序中。**

这样设计以后，你增加一个新的标准类型，原则上只需要：

1. 增加一个**审核准则文件**；
2. 增加/修改对应的**审核配置文件**；
3. 不需要修改核心审核引擎。

这会非常适合你现在正在设计的**标准化文件智能审核系统**。

另外，我建议你下一步把你现在的“通用性审核要求、GB/T 1.1-2020逐条审核、GB/T 20001.10逐条审核”进一步统一成一个**标准化的 Rule Set 数据结构**。这样以后不论是 GB/T 1.1、GB/T 20001.10，还是其他标准，都能用同一个引擎加载和执行。
